# 后端恢复、需求收敛与持续发布方案

日期：2026-10-17（Asia/Shanghai）。本文件是现状调查和后续实施方案；尚未执行应用恢复、数据库迁移、清库或重新部署。

## 1. 结论

建议保留当前服务器、域名、Caddy/TLS、PostgreSQL 和业务实现，先修复部署器，再完成一次应用部署基线整理。当前证据不支持重装操作系统或重写后端。用户已说明后端暂无使用者、允许清理，因此不需要为了保留测试玩家、旧房间和旧成绩设计复杂迁移兼容。

按用户本轮补充，建议将身份方案收敛为：**游客只玩本地；真实登录后使用排行榜、好友房间和联机对战。** 停止匿名联网，不再继续扩展临时游客身份。通用用户 ID、平台身份映射和游戏范围授权仍然保留。

优先顺序：部署失败及恢复路径 → 登录和授权收敛 → 配置中心首次上线 → 三游戏真实线上验收 → 固定日常发布入口。

### 2.2 已复现的根因

失败候选为 `0d7bfdfe4087-1792248271760-eb122d`。远端 journal 的有限字段为：

```json
{
  "phase": "database-unknown",
  "barrierAttempted": true,
  "domainInvoked": true,
  "newActivationAttempted": false,
  "verifiedNotCommitted": false,
  "stopped": ["management", "kart", "runtime"]
}
```

数据库只读元数据查询确认存在旧 `admin_console` 认证表，没有 `game_control` schema。候选私有目录中只有 journal，没有该候选的数据库备份或 precommit 证明。

执行身份不一致是可确定复现的故障：

1. `scripts/deploy-admin.mjs:799` 用 SSH 登录用户直接执行 `python3 .../control-deploy.py`；实际有效 UID 为 1000。
2. `infra/admin-console/control-database.py:420` 的第一条业务检查要求 `os.geteuid() == 0`。
3. 以相同普通用户调用实际候选 helper，第一条检查返回 `CONTROL_OWNER_REQUIRED`。探测先断言非 root，确保不会越过该检查，不执行迁移或写入。
4. helper 返回 `outcome=not_committed`，但因为尚未采集旧状态，`oldDataUnchanged=false`。
5. `infra/admin-console/control-deploy.py:766` 同时要求这两项恢复证明；未满足即记录 `database-unknown`，保留入口和三服务停止。

实际复现输出：

```json
{
  "code": "CONTROL_OWNER_REQUIRED",
  "outcome": "not_committed",
  "oldDataUnchanged": false,
  "mutationReached": false
}
```

远端 helper SHA-256 为 `55168636acfa30e302489acd96eb99335cf513550e9c62fb64d13f7f7773c536`，与候选 manifest 相符。这里的 `oldDataUnchanged=false` 表示缺少证明，不是检测到数据被修改。

还有两个恢复问题：当前 `--recover-control` 对此 journal 要求数据库已经是 schema2，而现场 schema 不存在；重新 adopt 同一候选又会遇到已有 journal。单纯重跑命令不能完成恢复。直接给整个命令加 sudo 也不是完整修复：私有目录与 journal 当前属于 UID 1000，而 coordinator 校验它们属于当前执行用户。

## 4. 身份方案：游客本地玩，登录后联网

采用此方向，可以删除临时游客的八小时生命周期、匿名续期、刷新丢失房间身份等产品复杂度。排行榜和好友关系需要稳定身份，匿名网络身份并不是当前核心需求。

目标规则：

- 游客不申请后端身份，不调用玩家业务接口；保留本地关卡、存档、单机/同屏玩法和本地提示。
- 排行榜、好友房间、联机对战统一要求登录。健康检查等运维公共端点单独保留，不代表游客拥有业务权限。
- 平台凭据由服务端换码或验证，按平台类型、AppID、平台用户 ID 映射稳定 `userId`。昵称、头像、属地仅记录实际可取得的内容；不把自报属地称为平台认证资料。
- 不增加跨平台账号自动合并；后续确有需求时再做显式绑定。保留通用 ID 格式，不因游戏不同复制账号体系。
- 通用账号与游戏访问凭据分开：服务端根据已验证平台应用映射、开放游戏和账号权限签发限定游戏的会话；房间、成绩、票据始终按数据库实际所属游戏核对。
- 网页脚本和 Origin 无法证明“官方客户端”。不要把前端 gameId 或客户端内嵌密钥当成应用认证。真实平台验证、会话 scope、资源所有权和权威结算承担不同职责。
- 停止签发临时及持久游客凭据，并在共享鉴权、refresh、相关升级入口拒绝旧游客。不要仅修改三款前端；否则旧包或直接 HTTP 请求仍可使用后端。
- 业务若保留公开排行榜必须另作明确产品选择；本方案默认排行也要求登录，减少例外。
- H5 没有接通真实登录时，继续提供离线玩法；不通过浏览器自行生成账号、伪造平台登录或退回匿名联网。

当前三款 H5 构建固定使用 `platform: h5`，正式包强制 `ephemeral`，尚未走公共客户端已有的“平台 SDK → code → 后端换码”分支。清单中的 `taptap-h5` 或广告 SDK 接入不代表玩家登录已经接通。因此补齐实际宿主登录与服务端验证是三款线上联机交付的前置工作；若目标 H5 宿主无法提供受信凭据，需要先接独立的玩家登录入口，该入口在完成前保持离线。不能仅改平台字符串或在生产注入测试身份。

最小改动覆盖 `session-routes.ts` 的 guest/refresh/upgrade、`identity-store.ts` 的默认签发、`auth.ts` 的共享鉴权与事务复查，以及 `game-routes.ts` 当前可匿名读取的排行榜。客户端要同步修改 `platforms/competition/client.js`、`scripts/competition-h5-service.mjs`、三游戏联网入口/自动上传和对应矩阵；部署镜像能力合同也须跟随新身份规则更新。共享鉴权的真实消费者不止三款，验证范围必须包含受影响的其他 Competition/Kart 入口，不能只隐藏三款游戏按钮。

这一调整不要求把管理 GitHub 登录复用于玩家。管理成员白名单、Cookie/CSRF 和玩家平台身份/Bearer 继续分离。

广告仍独立于联网开关：`H5_ADS_ENABLED` 默认 0；开启但 `TAPTAP_<GAME_ID大写下划线>_AD_UNIT_ID` 缺失或空白时仍为 off；非空但非法值构建失败。有有效广告位才进入 host 模式，只有真实完成返回才能发放对应奖励。无广告位的提示/支援直接执行，保留原玩法次数和辅助成绩规则。H5 广告位为构建输入，修改云服务器环境变量不会自动改动已经发布的静态游戏包。

## 5. 一次恢复与重部署的实施顺序

### A. 先修部署器，并收敛首次采用与日常更新

建议沿用当前具备 Docker 权限的固定部署账号，统一 helper、coordinator 和私有目录的属主约定；不混用普通用户创建 journal、root 执行 helper。数据库 SQL 仍由部署阶段的数据库 owner 执行，业务进程继续使用最小权限应用角色。不是放宽目录到 777，也不是让业务容器使用数据库 owner。

变更范围至少包括 `scripts/deploy-admin.mjs`、`infra/admin-console/control-deploy.py`、`control-database.py`、对应测试与部署说明。必须先查调用者和现有角色/目录合同再实现，不能只删一条断言。

停机前完成执行用户、目录权限、Docker/Compose、候选文件哈希、数据库版本、迁移前提、磁盘空间、镜像能力与代理配置检查。缺权限、缺文件、镜像不兼容等确定错误必须在服务仍运行时失败。

将“尚未发出 SQL 的确定失败”和“COMMIT 已发出但结果未知”分开记录。前者可以根据准确容器/候选/阶段证据恢复旧应用；后者仍须核验数据库后向前恢复。失败输出保留有限的阶段、原因枚举、迁移是否提交、可执行恢复动作，不输出原始秘密或 SQL 参数。

增加一条完整边界测试：使用与生产相同的非 root 部署身份，从 CLI/coordinator 调到真实 helper，验证错误发生在停机前。补足服务已停但迁移尚未开始的恢复场景。原来以 root 验证数据库 helper、mock 验证 coordinator，未覆盖两者真实组合。

### B. 整理本次失败事务

记录现有镜像、指针、journal、数据库 schema 与应用配置引用；原有 journal 作为故障记录保留，不伪造 completed。

本次已复现失败位于 helper 首条检查。修复后的专用恢复步骤应重新核对同一候选、旧容器与数据库阶段，然后结束这次未开始迁移的事务。不能把一般的 `database-unknown` 一律当成未提交，也不能靠删除 journal 强行重试。

后端暂未使用，可在此次维护中清理测试游客、成绩、房间和失败候选，省去游客数据迁移。清理范围以实际容器、卷、schema、release 身份列清单；官网、Caddy 证书及真实平台/OAuth 配置不属于待清理的测试数据。

### C. 建立新的应用发布基线

先完成三款游戏所用渠道的真实登录接线、服务端换码/验证和游戏范围授权，再更新联网包；期间可先交付后管恢复，但三游戏联机验收仍保持未完成。删除游客路径后，离线可玩与两个真实账号联网必须分别验证。

默认在现有 PostgreSQL 上执行正确迁移，复用 `admin_console`，建立 `game_control` schema2 及对应应用权限。完成登录专用后端策略，激活兼容的 Runtime、Management 与当前耦合的 Kart 镜像，设置实际控制开关。

当前三游戏本身不依赖 Kart 对局能力，但首次采用工具仍统一处理 Runtime/Kart/Management；本轮保留此拓扑，不额外做拆服务工程。日常更新继续按所选服务执行，Runtime 重建如影响 Kart namespace 则按现有规则伴随重建。

随后部署管理静态资源和 nonce 合同，核对管理 `/api/control` 路由，再按内部就绪 → Nginx → 真实 HTTPS → 业务检查的顺序开放。写入准确 sourceSHA、实际镜像 ID、schema 版本和活动配置版本。

如果数据库或历史部署目录确实存在大量无法解释的状态，可采用干净基线替代：在同一服务器重建本项目应用部署目录及应用容器，必要时初始化空的 `small_games` 库，再应用现有迁移和种子管理员。该分支不做旧测试数据迁移；仍需先修部署器、保留 TLS/登录配置并验收。它是清理项目部署，不是必须重装服务器。

## 6. 后续持续更新方案

### 6.1 日常操作保持简单

日常流程固定为：**提交并推送 dev → 确认该 SHA 的相关检查 → 从干净候选构建一次 → 部署所改服务 → 公网验收 → 保存回执**。远端 dev 若推进，按仓库规则重新合并并验证最终候选；不能把旧报告套到新 SHA。

建议新增一个薄的云发布入口，复用现有构建、传输、锁和激活逻辑，只负责选择受影响服务并生成统一回执。该入口尚未实现，不把它当成现成命令。无需引入 Kubernetes、新数据库或另做后台平台。

修复并完成首次采用后，现有命令的用途如下：

| 改动                  | 已有入口                                                      | 边界                                                    |
| --------------------- | ------------------------------------------------------------- | ------------------------------------------------------- |
| 后管页面/Management   | `pnpm deploy:admin --reuse-remote-config`                     | 依赖 schema2 与有效控制证明；复用远端配置               |
| Runtime               | `pnpm deploy:backend --services runtime`                      | 日常应用更新，不执行数据库迁移；按需重建 Kart namespace |
| Runtime/Kart 同时更新 | `pnpm deploy:backend --services runtime,kart`                 | 只构建和替换选择的后端                                  |
| 只读后端预检          | `pnpm deploy:backend --services runtime --check`              | 不等于业务验收                                          |
| 代理/域名路由         | `pnpm deploy:caddy --proxy-only`                              | 单独部署入口，不和每次业务更新绑定                      |
| 官网                  | `pnpm deploy:company`                                         | 与游戏后端独立                                          |
| 后管应用回退          | `pnpm deploy:admin --rollback`                                | 仅兼容 schema2 的管理版本，不回退数据库                 |
| 后端应用回退          | `pnpm deploy:backend --services runtime --rollback <release>` | 以实际选择和兼容性为准，不恢复旧数据库                  |

以上是**首次恢复完成后的操作表**。当前故障现场不能直接用日常命令恢复。旧 `deploy:tencent` 在 managed ingress 存在时已被阻止；不要删除标记后重新接管入口。通用 `deployment:bundle` 也不是当前云端既有数据库/代理的无缝替代安装器。

### 6.2 三类更新分开处理

- **应用更新**：构建受影响服务及实际依赖，复用服务器配置；无迁移时不重复完整数据库恢复演练，不跑无关游戏浏览器。
- **数据库更新**：显式迁移阶段及版本记录，使用一次针对本次迁移的备份和恢复验证；应用支持当前 schema 后才切换。应用回滚不自动回滚 SQL。
- **后台配置更新**：白名单、角色、CORS、游戏开关走后管发布及审计，正常情况下不重新构建、不重启所有容器。涉及环境秘密的配置独立维护。

正常 git hooks 和准确候选检查保留；部署命令不再重复历史全量测试。任何测试跳过必须在回执中说明，不能把 `qualityChecks: not-run` 写成通过。

### 6.3 自动化分两步落地

先让同一个发布入口在本机可靠工作，并完成一次成功发布与一次受控回退；随后增加独立的 GitHub 云部署 workflow，最初手动选择经过验证的 dev 候选。稳定后可调整为 dev 的相关 CI 成功自动触发。

workflow 复用同一发布逻辑，按服务器设置串行部署锁；新的提交排队，不能取消已经进入迁移/切换阶段的部署。一次构建生成带 SHA/文件摘要的制品，再部署该制品；后续采用镜像仓库时按不可变摘要拉取，不用浮动 latest。

GitHub 只持有部署所需凭据；数据库、OAuth 和平台密钥留在服务器私有配置。Pages 发布和后端部署分别显示结果；任一成功不替代另一个。

### 6.4 让“部署是否生效”一眼可见

每次保存一份脱敏回执：候选 SHA、部署工具 SHA、服务镜像 ID、schema 版本、控制配置版本、管理静态摘要、开始/结束时间、各步骤结果、回退目标和线上探测结果。管理站增加只读版本信息，敏感运维详情留在受控接口/回执中。

监测管理会话匿名 401、游戏 readiness 与轻量业务接口，不能只检查首页 200。发布后的服务崩溃、数据库不可用、GitHub 登录上游持续超时、证书续期和备份失败要有明确记录。监控/通知尚未创建，后续在实施发布流程时配置。

旧 release 和失败制品在成功验收后再按保留策略清理；保留当前版、一个已验证回退版及必要诊断，不把无限积累历史目录作为恢复机制。
