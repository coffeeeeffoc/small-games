## 原因与改动

HTTP 的公共 CORS 钩子原先为每次请求单独开启控制投影事务。独立控制数据库只有一个执行槽和五个等待槽；健康数据库下，突发请求也会因重复读取挤满队列而返回 `CONTROL_UNAVAILABLE` 503。真实 PostgreSQL + HTTP 的修复前回归中，48 个请求只有 6 个返回 200，42 个返回 503；公网同条件探针的 480 个请求有 156 个 503。

`createCompetitionControl.publicCors()` 现在只合并尚未开始事务回调的请求，开始读取前即封闭批次。之后到达的请求进入下一次读取，不缓存已完成的策略、不引入 TTL，也不扩大连接池和五项队列。业务策略、killEpoch、Kart 租约、发布锁、摘要校验、两秒总预算及失败关闭保持原约束；应用报告仍仅在确认 COMMIT 成功后记入内存。
