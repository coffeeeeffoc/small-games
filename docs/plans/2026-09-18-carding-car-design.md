# carding-car 首版设计

状态：Q1–Q12 均已确认，用户已调用 implement 技能开始实现。实现与验证记录见同目录实施计划及游戏内 playtest 文档。

目标目录：`games/local/carding-car`。沿用用户指定的目录名。

## 已核实的仓库条件

- 目标目录存在且为空，适用根目录的仓库约定。
- 仓库已有 React Three Fiber、Drei、Rapier、Zustand 的浏览器示例；本游戏已选 Creator，不直接复用这些浏览器入口。
- Hyper3D / Rodin MCP 可调用；生成会消耗额度，当前未发起生成。
- 若接入现有 Web Shell，需要补 standalone 清单、Shell workspace 依赖、锁文件和实际浏览器检查；根 workspace 已覆盖 `games/local/*`。
- 当前 `packages/canvas-game-adapter/src/index.ts` 的 Canvas 目标与 surface 使用 2D context；现有 `travel-bund` 的 R3F 入口依赖浏览器 DOM。不能仅登记原生构建就让该 3D 游戏原生运行，需按首发渠道另行验证。
- 已找到微信开发者工具 `D:\微信web开发者工具\cli.bat`；对 PATH、常见安装路径与卸载项的有限检查未找到 Cocos Creator 或 B站开发者工具，实施时先定位或补齐所需工具链。

## 已确定的目标

制作驾驶本身值得反复玩的 3D 街机卡丁车游戏。优先级为驾驶手感、赛道节奏、反馈、AI 竞争性、视觉效果、内容数量。

首个可玩版本包含：

- 一条完整赛道，一辆玩家车、三辆 AI 车，三圈比赛。
- 手机为主要使用设备，从第一版开始按手机输入、画面尺寸与性能预算设计；桌面键盘用于兼容试玩与开发验证。
- 首版需覆盖微信原生小游戏、B站原生小游戏和 H5；制作与验收优先级为微信／B站原生在先、H5 在后。
- 手机横屏、自动加速，左手转向，右手漂移和刹车。
- WASD / 方向键控制，加速、刹车、转向、漂移、漂移蓄力 Boost、碰撞。
- AI 行车线、圈数检测、检查点、排名、速度显示、起跑倒计时、完赛页面。
- 长直道、普通弯、S 弯、发卡弯、轻微跳台或高低差，以及风险更高但更快的路线。
- 以近几年中端手机为性能基准，目标 60 FPS；同时保留普通桌面浏览器稳定 60 FPS 的要求。具体机型、分辨率及测量结果单独记录，不以桌面模拟代替真机达标。

驾驶采用街机物理，不以真实赛车模拟为目标。通过统一 `KartConfig` 快速调整 acceleration、maxSpeed、steering、steering-speed curve、grip、lateral friction、drift、drift angle、boost、drag、collision response、camera lag、camera FOV、camera shake。

## 已确定的制作约束

- 已选 Cocos Creator + TypeScript，优先采用 3.8 系列并在实施时固定经渠道验证的补丁版本。React Three Fiber、Drei、Rapier、Zustand 和 Vite 不再作为游戏首版必需依赖，H5 由同一 Creator 工程导出。
- 赛道由 spline / curve 程序化生成，不整体生成赛道模型。
- Hyper3D / Rodin 优先用于车辆、轮胎护栏、路锥、树木、岩石、标志、看台、路灯等视觉资产。先程序化占位验证驾驶，再优先生成车辆，首批最多三次生成任务（含重试）；具体环境资产后定。
- 视觉模型与碰撞体分离。碰撞体优先 Cuboid / Capsule / Cylinder，不直接拿复杂视觉模型做碰撞。
- 美术统一为玩具比例、柔和圆润、色彩鲜明、干净有趣的 stylized arcade 风格。
- 模块职责至少覆盖 KartController、KartPhysics、KartConfig、Track、TrackGenerator、RaceManager、LapSystem、CheckpointSystem、RankingSystem、KartAI、RacingLine、ChaseCamera、HUD；在 Creator 中实现为职责明确的 TypeScript 模块／组件，不堆进巨型入口脚本。

道具箱、导弹、香蕉皮、护盾、不同车辆属性、更多赛道和角色均在核心驾驶稳定后再考虑。基础赛道中的轻微跳台或高低差属于首版要求；额外的跳跃玩法与 Boost pad 后置。

## 验证与迭代要求

每个主要阶段都启动实际游戏、浏览器操作车辆、检查控制和 console、记录 FPS 与明显性能问题、截图复查视觉。验证从第一阶段包含手机视口与触控，不等桌面版本完成后再补。然后列出最影响乐趣的三个问题，先修最大的问题并重新实测。

浏览器手机视口和触控模拟用于检查布局及输入行为，不能作为手机真机帧率、发热或触感达标的证明；真机结果单独记录。

每轮回答：“玩家只玩五分钟，为什么愿意再玩一次？”答案不明确时优先改善驾驶、漂移与赛道，不增加系统。允许删掉不好玩的机制、重构实现、调整数值和重做赛道。

每个经过验证的明显改善版本创建范围明确的本地 git commit，提交说明描述实际改善。浏览器操作与性能记录不能替代玩家对主观手感的确认。

## 已确认的首轮决定

用户确认 Q2–Q5 按推荐执行，并明确游戏主要用于手机。

1. 首版验收设备：手机优先，撤回“先验收桌面键盘”的建议；保留键盘操作。
2. 漂移学习门槛：容易进入、容易救回的街机漂移，技巧主要体现在入弯时机、线路与释放 Boost 的位置。
3. AI 公平策略：相同车辆性能，以不同刹车点和线路体现水平，不随玩家排名暗改速度。
4. 比赛节奏：三圈约三分钟，失误后容易继续，结算可立即再赛；以改善线路、圈速和名次形成重玩动机。
5. Rodin 资产投入：先用程序化占位验证驾驶，再优先生成一辆 Kart；首批最多三次生成任务（含重试）。

## 已确认的第二轮决定

用户接受 Q7、Q8 的推荐，Q6 选择三端首版支持，并进一步明确原生小游戏是主要目标。

6. 手机首发环境：微信／B站原生小游戏为主要目标，H5 次之；保留首版三端支持的要求，先验证原生 3D 启动、资源、输入及性能。
7. 手机操作：横屏双拇指、自动加速、左手转向、右手漂移和刹车。
8. 手机性能基准：近几年中端手机，目标先按 60 FPS 设计；具体机型与真实性能单独记录。

关于桌面开发与手机适配：电脑上开发和调试可以继续，但第一版必须按手机交互与性能预算制作。键盘和触控应表达相同的转向、油门、刹车、漂移意图，物理与比赛规则不绑定具体输入设备。手机画质从分辨率、阴影和可见模型数量控制。这些安排减少返工，不等于承诺 H5 可以直接迁入原生小游戏。

## 已确认的引擎方案

9. 用户选择 Cocos Creator + TypeScript，原生发行优先。采用微信发布流程与 B站适配插件，再导出 H5；接受 Creator 工具链，R3F、Drei、Rapier 不再作为首版必需。原模块职责、程序化赛道、KartConfig、独立碰撞体及 Rodin 制作流程保留。

第一阶段先验证三端最小 3D 场景、模型与纹理、触控、碰撞、音频及前后台恢复；通过后再进入完整赛道和手感迭代。官方文档支持某种引擎或接口，不等于本项目已验证通过。

## 已确认的具体玩法

10. 漂移奖励：按住漂移并在转弯时蓄力，松手释放；直线按住不蓄力。两档奖励以火花颜色和音效区分，撞墙或复位清空未释放蓄力。用户授权阈值、时长与加速强度通过试玩调整。
11. 失误恢复：撞墙减速并沿墙滑走，离开路面减速，卡死或掉出赛道约一秒后复位到最近合法位置；不扣圈、不判负，复位不能跳过检查点。
12. 赛道：晴天海湾玩具风格；风险路线为绕过发卡弯的狭窄近道，任何车均可进入。成功省时，撞护栏或掉落的损失超过正常路线；普通轻微跳台设在宽路段。

程序化赛道保留长直道、普通弯、S 弯、发卡弯和轻微跳台／高低差。首轮布局按“起终点长直道 → 普通弯 → S 弯 → 发卡弯及近道 → 宽路段轻微跳台 → 出弯回直道”制作，再按驾驶实测调整长度、宽度和曲率；三圈约三分钟是目标节奏，不通过篡改计时或 AI 速度强行实现。

## 实现时必须保持的比赛语义

- 圈数只在合法经过赛道路段并正向跨越终点后增加；来回压线、逆行和复位不增加圈数。
- 近道与主路是合法分支，分流前和汇合后共享进度边界。不能让近道因漏掉主路内部检查点而无效，也不能允许从草地任意切到后续路段。
- 排名根据有效比赛进度计算；合法分支的进度要对应同一个赛段，不能只比较距终点的直线距离。
- 复位回到已验证的合法位置，清理漂移状态，不增加进度；车辆接触与对手同样遵守物理约束。
- AI 使用相同车辆参数及碰撞、近道规则；以不同刹车点、行车线和可控失误形成竞争，不能传送追赶。
- 触控中断、切到后台、暂停和重新开始都要清理按压状态；恢复后不能出现油门、转向或漂移卡住。

上述内容是检查点、排名、公平竞争和快速恢复要求的实现约束；具体数据结构和数值由实现与实测决定，不额外建立通用赛车框架。

## 实施与验收顺序

1. **原生运行验证**：定位或补齐 Creator 与渠道工具，固定引擎及 B站插件版本；用最小 3D 场景验证微信和 B站的构建、资源、模型纹理、触控、碰撞、声音及前后台恢复，并导出 H5 验证。先排除渠道阻碍。
2. **驾驶与漂移**：占位车、短测试路段、统一 KartConfig；调顺低速转向、随速度变化的转向、抓地、漂移进出、两档 Boost、碰撞恢复和跟随镜头。实测多指同时转向与漂移。
3. **完整赛道与比赛**：实现海湾闭环、近道、跳台、三辆 AI、三圈、倒计时、有效圈数和排名、完赛与立即重赛；用主路与近道共同检验驾驶价值。
4. **反馈与资产**：核心驾驶稳定后使用最多三次 Rodin 首批任务，优先车辆；补漂移火花、Boost 感受、轮胎／发动机／碰撞音效和统一环境视觉。
5. **回归与性能**：逐渠道验证完整比赛、暂停恢复、连续重赛和资源清理；在实际设备记录配置、持续运行帧率与明显卡顿，再完成 H5 Shell 接入及相关仓库检查。

每个阶段都按前述“运行、操作、检查 console／日志和性能、截图、选前三个乐趣问题、优先修最大问题、再测”的循环执行。每个明显改善且经过验证的版本创建本地提交。

最小规则检查覆盖：倒退／反复压线不刷圈，主路和近道均可合法完赛，复位不跳进度，直线不刷漂移奖励，碰撞清未释放蓄力，三圈正确结算。真实操作检查覆盖：低速转向、S 弯连续操作、漂移两档及释放、撞墙脱困、近道成功与失败、起跑到完赛与重赛。

“有明显乐趣”的验收通过实际试玩判断：操作后果清楚，失误能恢复，下一圈能尝试更好的入弯／释放／近道选择，练习确实改善圈速或名次。自动化通过只能证明规则与操作链路，不代替主观试玩结论；不以增加道具或美术数量掩盖驾驶问题。

## 技术调查依据

- [Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)：当前渲染器使用 WebGL2，r163 起不再支持 WebGL1。
- [B站 WebGL2 适配](https://miniapp.bilibili.com/small-game-doc/engine/webGL2)：原生 Android/iOS 的 WebGL2 路线需要相应高性能模式配置，需在目标运行环境验证。
- [Rapier 入门](https://rapier.rs/docs/user_guides/templates/getting_started_js/)：JS 版本依赖 WASM，compat 版本嵌入 WASM 字节，不代表消除了 WASM 依赖。
- [Cocos 发布微信小游戏](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)与[B站 Cocos 适配方案](https://miniapp.bilibili.com/small-game-doc/engine/common)：提供已有发布和适配路径；B站插件、引擎版本及 WASM 配置仍需按实际构建验证。

## 实施中落实的事项

- 工具链与渠道接入：落实 Creator、B站插件、对应渠道工程配置与实际启动验证；不强行复用现有只支持 2D 的启动画布。
- 调参：根据试玩调整漂移阈值、转向、碰撞减速、约一秒复位时间、赛道尺度、近道代价与 AI 节奏。
- 性能：在真机验证前落实具体机型、系统、平台客户端、分辨率、画质、测试时长和测量口径；实际无法验证的环境单独标明。
- 资产：在手感验证后确定模型面数、纹理和材质预算；优先一款 Kart 复用为玩家与 AI，不扩大车辆数量。
