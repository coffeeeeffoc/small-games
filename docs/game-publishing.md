# 小游戏上架资料规范

适用于每款现有及新增小游戏，包括[早期八款](game-development.md#早期八款的改造边界)。新增、修改游戏、达到基本玩法闭环、改变名称／玩法／视觉、准备上架或交付时，AI 必须主动读取并核对本规范，不能等用户另外要求制作素材。纯公共规则文档维护不等于一次全游戏素材生产任务，也不能据此宣称全部游戏已经满足本规范。

## 统一目录与固定状态文件

每款游戏源码根目录使用 `publishing/`，与 `docs/design/` 的过程资料分开。子模块游戏同样放自己的仓库内，提交素材后更新父仓库 gitlink。游戏 README 链接 `publishing/STATUS.md`，所有平台从这个入口查找资料。

```text
<game>/publishing/
  STATUS.md                 # 唯一的当前进展、素材清单与阻塞记录
  copy/
    introduction.md         # 游戏简介
    tagline.md              # 一句话推荐语
    developer-note.md       # 开发者的话
  icon/                     # 游戏图标
  promo/images/             # 宣传图
  promo/videos/             # 宣传视频
  gameplay/screenshots/     # 实际游戏内截图
  gameplay/videos/          # 实际游戏内录屏
```

媒体文件名应能辨认内容、方向／尺寸及必要版本。渠道特供版本放对应类别下的 `<platform>/` 子目录，在状态文件中逐一登记；不为每个平台再复制整套规范或状态文件。需要隐私政策等额外资料时在同一目录增加并登记，不缩减上述八类。

已有正式素材先核对再归档复用。旧发布批次与回滚证据保留；可将确认有效的交付版本复制到统一目录并注明原始来源、版本／哈希，运行时引用的图标不贸然搬走。历史文件引用只作为迁移线索，不用散落路径或临时 `outputs/` 代替最终统一交付。大文件依仓库既有制品存储方式保存，目录中保留持久可访问的下载清单及 SHA-256，验证能取回；不新增大型二进制存储方案或提交密钥。

## 何时必须提供

**基本闭环**指玩家已能进入实际游戏，通过核心操作推进目标，得到胜负／阶段结果，并重试或继续；无胜负的创作／探索型游戏需能完成其核心任务并保存、导出或得到明确结果。不要求全部关卡、联网、广告或所有平台都已完成。

尚无闭环也应建立目录和 `STATUS.md`，先完成能真实描述的简介、推荐语、开发者说明及可制作的图像；无法录制尚不存在的玩法可以记录阻塞。达到基本闭环后，八类资料都必须有对应的实际内容，先交付与当前版本一致的基础版，再按目标平台规格更新。只有本轮可核实且解决不了的外部／技术阻塞才允许某项“暂无法提供”；游戏“还不够完美”、平台未选、缺广告 ID、关卡不够多、没排期、要等用户再说、没有主动尝试工具，都不是省略已有闭环素材的理由。

实际无法提供的例子：当前代码还不能完成核心操作而无法取得真实录像；经过诊断仍缺目标引擎／设备，无法录制所要求的该平台实机；图像／视频生成或录制工具实际失败且可用替代方案也失败。即便如此，其余可制作资料照常完成；手机浏览器录屏可先交付并准确标注环境，不能冒充原生真机。

## 只有两种逐项状态

`STATUS.md` 按[模板](templates/game-publishing-status.md)填写，每类必填，只有下列两种状态：

| 状态       | 必填证据                                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 已提供     | 实际文件的相对链接或受管理制品下载清单、对应版本、格式／尺寸／时长等信息、最近验证日期与方法；文件可打开且内容与当前游戏一致 |
| 暂无法提供 | 具体阻塞、失败或缺失证据、已尝试的解决方式、解除条件／下一步动作和复查时机；不能只写“暂无”                                   |

禁止用“可提供但未提供”“待制作”“待补充”“计划中”或空白作为交付状态，也不能把它们改个名字填进“暂无法提供”。检查时发现有能力制作的缺项，应在本次工作中实际补齐后标为“已提供”。占位文件、效果图冒充截图、未打开核验的链接、失效视频或不匹配旧版本不算已提供。

文件顶部固定记录 Game ID／名称、更新时间、当前版本或源码身份、目标交付形态、闭环是否成立及证据、当前上架阶段和下一步。素材完成、已上传、审核中、审核通过、上线分别记录；素材齐全不自动表示上架成功。每项“暂无法提供”在下次修改游戏时重新判断，阻塞解除即补齐，不无限沿用旧备注。

## TapTap 素材规格与内容要求

本节依据用户于 **2026-10-26** 提供的五张素材上传页提示截图整理，并按 **2026-10-27** 用户提供的横版宣传图、方版宣传图和宣传视频完整要求补充。其中 1:1 宣传图已纠正为至少 **1440×1440 px**，此前的 1024×1024 不满足这项封面要求。这是所示页面和用户提供文字的规格快照；正式提审前应在实际账号、游戏及 H5／原生／小游戏提交入口重新核对，并在 `STATUS.md` 记录来源、核对日期及差异，不能直接推定所有入口的要求相同。来源未说明的限制不自行补作平台硬性要求。

### 规格速查

下表尺寸均为最终文件的像素尺寸，比例均为宽:高；“至少”与“以内”分别表示下限与上限。

| 素材／存放位置                   | 数量、格式与大小                                                  | 比例、尺寸与时长                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 游戏图标 `icon/`                 | JPG／PNG；截图未注明文件大小上限                                  | 正方形，至少 **512×512 px**                                                                                            |
| 横版宣传图 `promo/images/`       | JPG／PNG，单张 **4 MB 以内**                                      | **16:9**，至少 **1920×1080 px**                                                                                        |
| 方版宣传图 `promo/images/`       | 上传竖版实机录屏后额外提供；JPG／PNG，单张 **4 MB 以内**          | **1:1**，至少 **1440×1440 px**；与横版宣传图核心视觉元素一致                                                           |
| 游戏截图 `gameplay/screenshots/` | **3～10 张**，JPG／PNG，单张 **4 MB 以内**                        | 横图宽高比 **8:5～8:3**，至少 **1280×720 px**；竖图宽高比 **3:8～5:8**，至少 **720×1280 px**；所有图片比例与第一张一致 |
| 宣传片 `promo/videos/`           | `.mp4`／`.mov`，编码 **H.264／HEVC（H.265）**，单个 **5 GB 以内** | 仅横屏 **16:9**，至少 **1280×720 px**，时长至少 **15 秒**；截图未注明最长时长                                          |
| 游戏实机录屏 `gameplay/videos/`  | `.mp4`／`.mov`，编码 **H.264／HEVC（H.265）**，单个 **5 GB 以内** | 宽高比 **9:21～21:9**，短边至少 **540 px**；**15 秒～30 分钟**，建议控制在 **2 分钟以内**                              |

截图比例范围与最低宽、高必须同时满足；不混传不同比例的横图、竖图。录屏与宣传片的比例、分辨率要求分别核对，不能互相套用。

### 游戏图标

- 不得使用**白底、黑底或透明底**；提交有完整背景的方形图。
- **不可自行切圆角**，不要把圆角外侧留白或留透明区域；圆角展示交由平台处理。
- 检查最终导出文件的背景与透明性，不能仅凭编辑器预览或扩展名判断合格。

### 宣传图

#### 16:9 横版宣传图

用于以下三个位置：

1. 首页推荐、今日游戏等使用卡片展示游戏的页面。
2. 横版游戏实机录屏、宣传片的视频封面。
3. 未上传实机录屏时，游戏详情页的首张图集图片。

文件要求：

- 宽高比为 **16:9**，最低尺寸为 **1920×1080 px**；更高分辨率仍须保持 16:9。
- **只支持 JPG／PNG**，单张文件大小在 **4 MB 以内**。
- 比例、宽高下限与文件大小上限须同时满足，不能以低分辨率预览图或仅改扩展名的文件代替。

画面要求：

1. **需要在图中添加游戏标题，但不得出现游戏标题以外的宣传性文字。** 标题应准确、完整、清晰可辨，不额外添加推荐语、卖点、下载口号等。
2. **不得出现游戏图标。** 标题字样与独立 App 图标不同，不能把图标作为画面角标放入封面。
3. **需要高清精美，不得直接使用游戏截图或简单拼贴。** 应形成完整的宣传构图，不能把截图加标题后直接当作宣传图。
4. **宣传图应贴近当前游戏的真实美术资产或者玩法，不得过度美化。** 不暗示尚未实现的玩法、角色或画质；宣传图不能冒充实际运行截图。

#### 1:1 方版宣传图（竖版实录封面）

**触发条件与用途：当前游戏上传了竖版游戏实机录屏时，需要额外上传一张 1:1 宣传图，用于竖版游戏实机录屏的视频封面。** 方版图是额外的封面素材，不替代横版宣传图，也不是游戏图标。

文件要求：

- 宽高比为 **1:1**，宽、高均不得低于 **1440 px**，即至少 **1440×1440 px**。
- **只支持 JPG／PNG**，单张文件大小在 **4 MB 以内**。
- 原先的 **1024×1024** 方图不能作为符合本项要求的最终交付，图标建议尺寸也不能套用到方版宣传封面。

画面要求：

1. **需要在图中添加游戏标题，但不得出现游戏标题以外的宣传性文字。** 完整保留正确的游戏名称，避免裁切标题或增加宣传语。
2. **不得出现游戏图标。** 不使用 App 图标、图标徽章或图标拼贴代替方版封面。
3. **需要高清精美，不得直接使用游戏截图或简单拼贴。** 为方形画幅组织完整构图，导出后查看细节与边缘清晰度。
4. **不同尺寸（16:9 与 1:1）宣传图的核心视觉元素应保持一致。** 制作时对照两张成品，核对主要角色及服装、核心玩法动作、场景主题、主色调与标题风格；可调整构图以适配方形画幅，但不能换成另一套角色、场景或美术风格。

两种画幅应成组检查。方图沿用横图对应的真实游戏资产或玩法方向；若缩放或重新生成用于达到尺寸要求，应记录处理方式，并以最终文件的尺寸、清晰度和体积为验收依据。

### 游戏截图

用于游戏详情页图集。正式上线开放下载或开放试玩时，必须包含展示**核心玩法**的实机游戏截图。

- 每张含实机画面的图片，**实机画面面积都必须超过 50%**；这是单张图片的面积要求，不是整组图片的张数占比。
- 实机画面截图放在最前列，不用首页、选关页等非核心玩法画面代替全部玩法展示。
- 平台截图栏允许概念类、广告宣传类图片**最多 2 张**。这类图片在仓库中仍归档到 `promo/images/`，登记上传顺序与用途，不能当作 `gameplay/screenshots/` 的真实截图证据；上传整组仍须满足 3～10 张、比例一致等要求。
- 不得包含充值、商城、抽卡等游戏商业内容。采集时选择合适的真实场景，不用效果图重绘运行画面。

### 宣传片

**用途：首页推荐及游戏详情页展示。** 为了保证首页推荐效果最佳，上传页允许额外上传新的宣传片视频；仓库在基本闭环后仍按八类资料要求交付宣传视频，平台选填不改变仓库交付要求。

文件要求：

1. **视频文件格式为 `.mp4` 或 `.mov`。** 必须实际导出为支持的容器，不能只重命名 WebM 等录制源的扩展名。
2. **视频编码格式为 H.264 或 HEVC（H.265）。** 容器扩展名合格不代表编码合格，需要检查实际视频轨道。
3. **单个视频文件大小在 5 GB 以内。** 核对最终文件体积。
4. **仅支持横屏，宽高比限制为 16:9，分辨率不得低于 1280×720 px。** 更高分辨率也须保持 16:9，不能沿用竖屏实录的比例范围或短边 540 px 下限。
5. **时长不少于 15 秒。** 本次来源未规定宣传片最长时长，不把实机录屏的 30 分钟上限套用为宣传片要求。

内容要求：

- **宣传片内容不得与实机视频内容高度雷同。** 应围绕已实现的玩法、美术和特色安排分镜、镜头或剪辑，形成有区别的宣传内容；不能把同一段实录改名，或只加标题后作为另一份宣传片交付。
- 竖屏实机录屏即使符合录屏栏要求，也不能直接充当该横版宣传片。宣传片与实际游戏录屏分别交付、分别登记和核验。
- 完整播放最终成片，核对画面、时长和实际内容；技术参数合格不自动证明内容差异合格或平台审核通过。

### 游戏实机录屏

用于首页推荐及游戏详情页展示。正式上线开放下载或开放试玩时，必须提供实机视频。

- 充分演示核心玩法：**前 5 秒内展示核心玩法，且核心玩法展示至少持续 10 秒**。不能用长片头、加载或菜单操作占满开头。
- 不使用**额外的人声配音及字幕**，不使用画中画，不露出手机等设备 UI；采集并复看最终游戏画面。
- 不展示折扣充值等纯商业化内容。
- 完整播放核对操作、反馈和画面真实性，并记录实际录制环境。桌面浏览器、触屏模拟或手机浏览器素材应如实标注，不能冒充未经验证的原生真机录屏。

### 交付前逐项核验

1. 检查实际文件的格式、字节大小、像素尺寸、宽高比、透明性；视频还要核对容器、编码、时长及能否完整播放。WebM 录制源需实际转码到支持的格式，不能只改扩展名。
2. 宣传图分别核对横版 16:9／1920×1080 下限、方版 1:1／1440×1440 下限、单张 4 MB 上限及仅标题／无图标要求；上传竖版实录时检查额外方版封面，并将两种画幅并排对照核心视觉元素。
3. 宣传片单独检查 16:9、1280×720 下限、15 秒下限、5 GB 上限、MP4／MOV 容器、H.264／H.265 编码及与实录的内容差异。再分别检查游戏截图数量／顺序、实机面积、实录前 5 秒与核心玩法持续时间，不能只检查技术参数。
4. 在 `STATUS.md` 对应行登记实际规格、验证方法和结果。基础素材已提供但尚未满足目标平台规格时明确写出差异；“已提供”不等于“可直接提审”或“审核通过”。

## 内容与主动检查

1. **查游戏**：实际阅读／运行当前玩法，确认名称、对象、核心操作、特色、已实现功能和闭环状态；文案只描述已实现内容，不暗示尚不存在的联机或奖励。简介、推荐语、开发者的话是三个独立可直接粘贴的交付文件。
2. **查素材**：逐一检查八类文件、来源与使用权、版本、打开／播放、实际画面和尺寸／时长。宣传图与宣传视频可以设计剪辑，游戏截图与游戏录像必须来自实际运行；两类视频分别交付。概念效果图只能标注为概念，不能作为实机证据。
3. **补缺项**：优先复用有效现有素材；实际生成图标与宣传图，实际录制核心操作与反馈，并制作宣传视频。玩法已有闭环就完成可制作的基础资料，不因缺正式平台账号而放弃本地录制。只有完成尝试后确认无法提供的项，才写具体阻塞。
4. **核规格**：有目标平台时核对当前要求及用户指定的尺寸、比例、时长、文案；TapTap 素材按上节逐类核对，并在实际提交入口复核。只有标题等明确要求照办。尚无平台时提供与手机方向一致的基础素材并记录规格，正式提审前再适配，不能凭空声明满足平台审核。涉及地图等审核反馈时同时检查运行画面、截图和录屏，不能只修宣传图。
5. **更新并复核**：填写 `STATUS.md`，确认没有第三种逐项状态、空链接或以计划冒充阻塞；交付链接指向统一目录，保存正式素材及其证据。玩法、名称、美术或入口变化后复查受影响资料，过时素材更新后再标已提供。

这是一项代理必须执行的交付检查；当前没有自动化脚本能仅凭状态文本判定“确实无法提供”。不能把写满表格视为检查通过，必须核对真实文件和阻塞事实。上架上传与提交审核仍遵循用户授权，本规范本身不授权对外发布。

## TapTap 图标规格与提示词
