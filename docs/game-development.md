# 小游戏通用开发与改造规范

本文件是游戏产品、移动体验和渐进改造要求的唯一正文。新建、维护、重构、接入平台或准备上架时先读本文件；独立、Shell 内置、iframe 和原生小游戏均适用，创作后管等内部工具不套用玩家界面要求。用户本次明确要求和已确认的单款设计优先；历史实现不能自动成为例外。来源与取舍见[梳理记录](agents/game-requirements-sources.md)。

## 每次改动如何执行

1. **检查现状**：读取游戏 README、最近设计与验证记录、实际入口及构建配置，对照下列规范和[上架资料规范](game-publishing.md)。列出本次涉及的缺口、现有素材、可复用公共能力和必须保留的存档、玩法、平台入口。
2. **决定范围**：任务涉及的页面、触屏、反馈、广告、配置等低风险缺口直接补齐。整体换引擎、大幅重做玩法、破坏存档或扩大平台范围，若尚未获授权，先给出具体改造建议并主动征求用户意见；继续完成不依赖该决定的原任务。已有授权直接实施，不重复确认。纯文档或局部规则修复无需借机全面换引擎。
3. **按依据实现**：新游戏与主要改版按“产品方案 → 效果图 → 代码 → 实际画面对照与功能验证”推进。方案、效果图、实际截图和验证记录放游戏现有设计目录，没有时使用 `docs/design/`。历史缺项不能静默略过；单款文档只记录差异、决定与证据，引用公共规范，不复制整篇规则。
4. **收尾检查**：逐项说明本次已补齐、确实不适用、需用户决定或有具体阻塞的内容，并更新上架资料状态。上架资料的状态和补齐义务以[专门规范](game-publishing.md)为准，不能用“下次再做”代替。提交前检查调用者、构建、注册、测试及实际平台消费者，执行[增量发布验证](operations/incremental-publication.md)。

新游戏完成验证后，代码、产品方案、效果图、验证记录和上架资料一起提交并立即推送远端 `dev`，无需再次询问；用户明确要求阶段性停下时遵从。现有游戏维护按当前任务的提交／推送授权执行。保留无关改动，远端推进后以最终合并候选重新验证。

### 早期八款的改造边界

用户于 2026-10-22 确认的“3+5”名单如下；这是**暂不默认推动整体重构／Cocos 迁移**的例外，不豁免当前改动的测试、广告可靠性、存档兼容或上架资料要求。已有 Cocos 实现继续维护，不逆向迁移；用户明确要求改造时照常执行。

| 批次 | Game ID                                                                                           |
| ---- | ------------------------------------------------------------------------------------------------- |
| 三款 | `cops-robbers`、`cops-robbers-realtime`、`xiangqi-five`                                           |
| 五款 | `vibeJam-myself-history-guess`、`wulong-city`、`night-overwatch`、`carding-car`、`letters-words2` |

其余现有游戏在被修改时主动对照本规范，逐步补齐；发现整体验证不足或需要整体迁移时提出可执行方案，不能只以“旧游戏”为由维持缺口。此规则不要求一次性重写全部游戏。

## 产品方案、Cocos 与真实玩法

- 新游戏和上述八款以外游戏的主要改造，优先采用 **Cocos Creator + TypeScript、移动端小游戏**路线。评估现有纯规则、关卡数据、素材、存档和公共 Host 的复用；因明确的 Web 工具性质、渠道限制或改动成本采用其他方案时，把理由、影响及用户决定写入该游戏设计记录。参考 [Cocos 决策背景](adr/0012-carding-car-cocos-creator.md)，具体工具链以当前工程和构建检查为准。
- Cocos 迁移应覆盖真实场景、渲染、输入、音频、生命周期与构建入口；保留引擎无关规则和内容层。复制旧 Web 页面、包一层 WebView、只改工程名称不算迁移完成。旧入口仅按明确用途保留，说明发布入口，避免长期维护两套分叉玩法。
- 先写清核心操作、玩家决策、目标、失败原因、胜负／阶段结算、重试与继续的闭环，再设计页面。操作要真正改变局面；角色、物理、碰撞、路线和反馈应支持可观察、可解释的因果关系。
- 保留已有好用素材、主题特征和核心乐趣；改版可以重做机制，但不把原有美术退化成随意的几何占位。涉及模拟、竞技或随机规则时，明确边界与公平性，并保留可复现验证。
- 缺少真实 Creator 或目标工具时，继续可独立完成的设计、规则和工程工作，记录具体阻塞及本地构建交接步骤；不伪造引擎声明、预构建制品或运行截图。只有已获用户授权的阶段性交付，才将未完成构建的阶段明确提交，不能声称验收完成。

## 手机画面、页面与反馈

- 从手机比例、触屏、安全区和平台胶囊开始设计，再适配桌面。新游戏、主要页面／场景新增和界面改版先生成效果图，至少覆盖本次涉及的首页、选关、核心游玩及关键状态；局部沿用风格可更新对应图，纯规则／文档改动不必重新出图。
- 每款游戏有自己的完整首页，突出“开始／继续”，有明确选关入口；没有传统关卡的玩法可提供与之对应的模式、章节或挑战选择。Shell 游戏目录不代替游戏首页。
- 页面按需组织为首页、选关、准备、游玩、成长／图鉴、结算、设置、帮助等精简小页面，返回路径清楚；只显示已实现且有用的入口。优先页面切换，必要确认与短反馈才用轻量覆盖层。
- 游戏画面保留必要目标、状态、触屏控件和暂停／返回入口，让场景占主要空间；开始游玩后收起 Shell 品牌顶栏和目录。规则与说明放帮助／提示；首次引导用短步骤、实际操作与即时反馈逐步引入。必要的失败原因和决策信息不能因“精简”被隐藏。
- 场景、角色、材质、颜色、按钮、图标、动画与音效围绕主题一致设计，具有游戏感和层次，避免单调的默认控件或后台面板。关卡／对象的可操作、选中、锁定、受阻、命中和成功状态清楚区分，不能只靠颜色或文字解释。
- 给点击、拖动、碰撞、得分、受伤、重要机制变化和胜负配置适量视觉与声音反馈；依玩法选择震动。提供音效／音乐等实际支持的设置，尊重静音、减弱动态及平台能力。震屏、hit-stop 只影响呈现，不改变权威模拟、碰撞、计时、网络时序，也不覆盖用户暂停。
- 为游戏设计自有图标和加载画面，替换默认 Cocos logo／slogan；加载、失败、重试反馈简洁。检查真实发行构建的首屏和资源引用，不能只改编辑器预览。图标也进入[上架资料目录](game-publishing.md)。
- 暂停图标使用两根等高、等宽、平行且分离的实心竖条，通过图标库、SVG、CSS 或 Canvas 绘制；不用 `Ⅱ`、`II`、`||`、`π`、`⏸` 等字体字符代替。保留“暂停”无障碍名称，Web 使用 `aria-label="暂停"`，并检查实际缩放后的形状。

## 触屏、方向与运行体验

- 核心玩法只靠触屏即可完成，直接点按、拖拽、滑动或长按场景对象；输入位置与效果关联明确。持续移动／组合动作提供不遮挡目标的拇指控件和多点触控；键鼠是补充，已支持时提供具体映射说明。
- 主要按钮有效热区尽量至少约 44 CSS px，Canvas 使用等效逻辑尺寸；检查间距、刘海、圆角、平台胶囊与窄屏。避免悬停依赖和精确鼠标定位；图标入口提供无障碍名称。
- 连续操作跟随手势，正确处理松手、取消、触点移出、失焦和多指切换，避免移动／攻击卡住。页面切换、暂停、前后台和退出管理输入、计时、音频及监听；恢复不补算大段离线时间，不重复输入，不复活已销毁实例。
- 横竖屏在方案和效果图阶段按玩法确定，所有页面统一适配。动作、竞速、横向战场优先横屏；单手点选、竖向棋盘等可竖屏，记录理由。浏览器横屏游戏在系统自动旋转关闭时仍可玩；方向锁失败时旋转完整容器或逻辑视口，涵盖控件、弹层、安全区与触控映射，不以“请旋转手机”阻断。
- 浏览器全屏不再作为新游戏或后续改造的默认功能、必备入口或交付要求，不因独立 Web/H5、iframe 嵌套或桌面预览自动增加控件。原生小游戏继续由宿主承载，普通视口仍须满足方向适配、安全区和触屏要求。
- 其他游戏已有全屏功能不因上述要求取消而批量移除；本次任务确实涉及其维护时，保留公共控制器、用户手势、拒绝降级、进度保持和既有安全契约。Shell／iframe 的 sandbox／CSP 边界不随单款游戏移除按钮而放宽。
- 控制首屏资源和移动渲染开销，按需加载素材与关卡。存储或可选平台能力失败时保持本地玩法，兼容旧存档，避免失败读取后覆盖已有数据。

## 关卡、成长与开发模式

- 关卡逐步引入机制、组合和难度，成长带来可感知的玩法变化；图鉴服务已出现或可解锁的角色、武器、机关等内容。避免堆数字、复制关卡或为了菜单而加养成。
- 关卡数量按游戏方案确定；100／1000 关等历史要求属于指定游戏。批量关卡需检查可解性／可达性、重复与实际难度，并做实际游玩抽样；随机开局也验证合法性和公平性，不能只用生成数量作为完成证据。
- 核心层负责规则、模拟、状态流转和结算；关卡配置独立描述地图、对象、目标、波次、难度、奖励、解锁与资源。已有机制的新关卡只增加配置、资源与登记；新机制先扩展可复用规则，避免按关卡 ID 堆特判。
- 每款 Game 拥有配置 schema、校验与必要迁移，遵循 [ADR-0007](adr/0007-game-owned-content-schemas.md)。稳定关卡 ID、首页选关、正常解锁和存档使用同一目录；检查引用、奖励、解锁关系和重复结算。
- 规则与内容不直接依赖 DOM、渠道 SDK 或 Shell，通过已有 Game Host 与环境适配层访问能力；不为单款游戏另造中央框架。
- Web/H5 正式构建保留显式开发模式，默认关闭；普通玩家按正常进度选关，开发者才可自由选关／调参，试玩奖励和排行隔离。全部开关优先级、共享源、跨 iframe 传递与验证命令只在[开发者模式约定](game-dev-mode.md)维护，不自行实现私有语义。

## 可选激励与公共能力

- 新游戏和相关改版主动寻找适合的可选奖励机会，如进阶提示、补给、临时增益、复活、结算额外奖励或非必需加速；正常开始、游玩、通关和基础成长无需广告。没有合适机会时说明原因，不强行插入；广告额度、效果、有效期及竞技限制写入游戏方案。
- 入口使用“提示”“补给”等具体功能名，进入领取流程清楚说明完整观看后的收益，并可取消。点击立即反馈；完成后奖励实际可见、可用；未完成说明未获得奖励。SDK 缺失、广告关闭或无库存不阻断正常玩法。
- 游戏声明奖励资格与结算，调用已有通用广告端口；渠道选择、AppID／广告位与 SDK 回调由构建、Host 和 Adapter 负责。按目标平台配置自动注入，游戏不硬编码渠道 ID，也不复制每个平台的玩法。近期实际接入优先 TapTap；微信、抖音、B站等按真实目标扩展共享接线及验证，不能把已有 Adapter 等同于全部游戏已接通。
- 广告控制权遵守 [ADR-0005](adr/0005-ad-authority-is-host-owned.md)；统一接口、成功／取消／失败、生命周期、迟到回调、幂等和当前平台边界只在[广告接入指南](operations/taptap-rewarded-ads.md)维护，配置字段与交付类型只在[构建指南](operations/game-builds.md)维护。新增问题更新对应公共指南，游戏文档仅补本游戏奖励与验证。
- 插屏、Banner、开屏不是默认必做；只有用户授权、目标平台真实支持且不破坏体验时接入。品牌加载页不能用强制激励替代，模拟广告不能作为正式渠道降级。
- 联网能力复用已有身份、存档、战绩与排行榜服务，按需接入。保持各入口身份边界和离线可玩，能力未启用时隐藏无效 PK／榜单入口；不能将客户端分数直接作为可信公开榜。服务部署、身份验证、服务端验分、UI 入口分别验证，配置地址不等于服务已上线。详见[服务架构](architecture/game-services.md)。分享对应当前游戏／关卡，清除 dev 参数，不凭打开分享菜单发奖。

## 验收与维护入口

| 改动                       | 最少需要的实际证据                                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 界面／交互                 | 手机尺寸下逐页对照效果图；触屏走通首页、选关、玩法、暂停恢复、结算与返回；检查遮挡、文字密度、目标发现、反馈、手势取消 |
| 横屏／全屏                 | 物理横屏、竖持兜底、关闭自动旋转、小屏安全区、触控映射；有全屏入口时验证进入／退出；原生检查方向配置且无浏览器全屏按钮 |
| 规则／关卡／存档           | 胜负、可达性／可解性、正常解锁、成长、幂等结算、存档恢复；复用现有测试                                                 |
| 广告／渠道                 | 按广告指南验证完整调用链、配置注入、四种结果、重入／旧局／迟到回调；实际目标制品与源码对应                             |
| 开发入口／构建             | 按开发模式与构建指南检查独立、Shell、iframe 等实际支持入口及默认关闭                                                   |
| 新游戏／玩法闭环／上架准备 | 检查并补齐统一上架资料目录及 `STATUS.md`，逐项验证实际文件与阻塞依据                                                   |

修改公共 H5 全屏机制运行 `pnpm test:h5-fullscreen`；其他检查按[增量发布验证](operations/incremental-publication.md)选择真正受影响的项目与消费者。纯文档整理检查内容、格式和链接，不重建全部游戏。

交付记录实际环境、源码／制品身份、关键截图和验证结果，区分概念图、桌面触屏模拟、真实引擎、平台 SDK、手机真机、上传、审核与上线。未完成的具体环节明确列出；本地通过、推送成功、CI 通过和 Pages 部署是不同事实。

修改通用要求时更新本文件或上面唯一负责该主题的指南，根 `AGENTS.md` 仅维护触发入口。历史设计、单次验收和任务记录保留证据身份，不作为新的规范副本；新增明确例外写游戏设计并链接回来。
