# 神机合阵：Cocos 移动端重构方案

日期：2026-10-22。状态：方案已获用户授权实施。以下保留方案基线；实际参数与验收边界以 README 和本目录验收记录为准。

## 1. 产品定位与重构边界

将 merge-front 重构为横屏、触屏优先的神话机关对攻小游戏：花灵石抽取残字，拼出神将与武器，在扩充生产阵容和累加升级之间决策；双方单位持续从各自水晶出生，在二维战场自由移动、就近交战，摧毁对方水晶获胜。

保留《神机合阵》名称、merge-front 身份、神话人物与机关题材。画面、页面组织、角色资产、关卡和核心战斗重新设计。首版实现完整人机闯关，核心规则具备未来服务端运行条件；真人房间和匹配后续接入。

### 现状依据

本轮读取了现有 `src/content.mjs`、`src/engine.mjs`、`src/main.mjs`、README、测试入口及旧方案。当前实现存在：

- Canvas/DOM/CSS 表现层，防守与进攻双模式。
- 三行四列部署台；寻敌带 `lane` 过滤，移动主要沿 X 轴。
- 指定购买残字，直接购买完整武器；同名同等级合成，三级上限。
- 进攻模式已有配方循环生产，但敌方由独立脚本增援，不走玩家经济和合成流程。
- 三位神将、三种武器，缺少本次要求的章节解锁体系。
- `merge-front:preferences:v1` 保存音效和胜场，没有新版关卡或对局存档。

现有规则已与新目标有结构性差异。保留合成事务校验、随机种子、生命周期等设计经验；不把旧三路循环包进 Cocos 继续沿用。

### 关键方案取舍

| 问题 | 推荐 | 原因与代价 |
| --- | --- | --- |
| 拼成后的作用 | 配置区保留兵符，持续召唤战场单位 | 扩军、升级、生产节奏都有意义；需清楚区分兵符与战场单位 |
| 一次性召唤方案 | 本版不采用 | 阵亡后反复拼同一姓名会增加操作负担，资源运气容易直接决定能否继续 |
| 美术实现 | Cocos 2D 角色与特效，俯视斜角的 2.5D 视觉 | 适合同时显示战场和配置区；无需为第一版制作完整 3D 世界 |
| 战斗模式 | 单一水晶对攻 | 关卡、AI、玩家对战共用胜负与经济规则 |
| 武器定义 | 能独立移动、寻敌、攻击的机关单位 | 与用户要求一致；第一版取消旧版专属装备和邻接合体，降低规则负担 |
| 成长 | 局内等级无设计上限，局外解锁内容 | 后续公平对战无需继承永久攻击数值 |

## 2. 一局游戏的闭环

选关 → 查看敌方风格与通关奖励 → 选择本局残字池 → 进入战斗 → 抽字、拼装、扩军或升级 → 自动出兵交战 → 水晶摧毁 → 结算解锁。

初期建议的 3–6 分钟为待测目标。当前快速合法策略约 37–61 秒通关，首关触屏策略约40秒模拟时间；本版先保留短局节奏，真人局长和后期难度继续用真机试玩校准，不把脚本策略当真人平均表现。

### 2.1 三层对象

1. **残字**：局内材料，例如「哪」「吒」或「离」「火」「铳」；按“所属配方＋字位”识别，不能只比较显示汉字，避免同字串配方。
2. **兵符**：完整神将或机关的生产配方，保存在下方配置区，包含等级与生产倒计时。
3. **战场单位**：兵符召唤的实体，拥有位置、生命、目标和攻击状态。阵亡不会删除兵符。

第一版建议战前选择最多 3 种神将、2 种武器作为本局残字池；初期不足时使用已解锁内容。配置区提供 3 个神将生产位和 2 个武器生产位，同类可占多个位。抽出的残字只来自本局已选择、且关卡允许的配方。局外解锁更多角色不会自动稀释当前对局的残字池。

### 2.2 灵石与随机残字

- 灵石是局内资源，主要由水晶稳定产出；击杀只给少量额外收入，避免击杀优势进一步锁死落后方。
- 提供“求将”和“铸器”两种抽取操作，选择神将池或武器池，池内结果随机。建议初始调参值为每次 30 灵石获得 3 枚残字。
- 双方拥有相同起始灵石、基础收入、价格、抽取规则和可用内容范围。初始配给确保可以拼成第一支部队，防止开局空等。
- 残字按类型堆叠，默认露出当前配方相关字块；不设满仓吞奖励，不要求在大量独立格子间寻找重复字。
- 建议每连续 3 次同类抽取至少提供 1 枚“当前已开始拼装配方的缺字”；触发条件、候选排序和次数均是公开规则，AI 同样适用。
- 为完全无用的重复字提供同类别“3 枚换 1 枚指定字”，仅能选择本局残字池；不会兑换出未解锁角色。不再叠加商店刷新、万能字和多种兑换货币。
- 扣灵石、抽取、入库是一笔原子操作；重复点击、余额不足或非法请求不发生半扣费。

抽取频率、字数和保底以完成配方的平均时间校准，三字、四字配方不能未经补偿就比两字配方更弱；可通过配方权重和基础强度共同调整。配方使用字位列表，支持重复汉字，不写死两字或三字长度。

### 2.3 拼装、扩军与无限累加

- 拖动残字到对应姓名或武器轮廓，补齐全部字位后形成一级兵符。支持“点残字、点目标”的替代操作。
- 新的完整配方可放到空生产位增加出兵，也可投入同类兵符升级。
- 同类兵符合并后等级相加：1＋1＝2、3＋1＝4、3＋5＝8。不要求同级，不设三星、99 级等玩法上限。
- 零散残字可以填入某兵符的下一份升级配方；填齐一套等级＋1。仅填一部分不提前加属性，可撤回未完成的材料。
- 不同神将、不同武器不能互相吞并；配方、等级和材料在一次成功事务中更新，失败保持原状。
- 兵符升级只作用于以后召唤的单位；已经出阵的单位保持出生时等级和受伤状态。避免升级同时给整支旧军队免费增伤、回血。
- 合并继承较保守的剩余生产时间，不触发立即出兵；移动兵符不重置为首次召唤。取消拖动、切后台、重复命令不能刷出兵。
- 生命、攻击采用基础值加线性等级增量；移速、射程和攻击间隔不随等级无限增长。多份低级生产位与一份高级生产位通过出兵周期、数量和受击分散形成取舍。
- 等级用数字显示，不堆叠星星。测试高等级合并、序列化和数值安全；移除旧指数增长公式。

全部局内灵石、残字、兵符等级在新对局重置。保存的是关卡进度、角色/武器解锁、图鉴记录和设置；离线人机的中途存档作为同一对局恢复。

## 3. 无分路的水晶战场

### 3.1 空间与移动

- 左右两端为双方水晶，战场是连续二维平面，逻辑中删除 `lane` 概念。
- 全部神将和武器从所属水晶的出生区域产生，经出生点疏散后向敌晶推进，允许斜向移动、绕开友军与追击敌人。
- 首版采用开阔战场，各章变化集中在美术和敌方组合；暂不加入迷宫、硬障碍或必须重做寻路的复杂地形。
- 配置位的位置不映射为战场通道。玩家第一版管理编队、材料和升级，单位自主行军；不增加逐单位微操负担。
- 轻量避让与分离解决出生重叠和近战围堵；被阻挡的近战改找目标周围可达攻击位，禁止站在后方无限播放待机。

### 3.2 寻敌和攻击的明确规则

出生 → 行进 → 发现附近敌人 → 靠近至有效射程 → 攻击 → 目标失效后重新寻敌 → 继续攻晶。

1. 优先选择警戒范围内最近且可达的敌方单位，不区分敌方神将与武器，不存在同路限制。
2. 距离超过自身射程时继续接近；没有单位目标时向敌晶移动，进入对晶射程后攻击。
3. 目标死亡、失效或追击距离过大时重新选择；使用小幅切换阈值避免在两个等距目标间来回抖动。
4. 已在攻击水晶的单位发现近处敌军时重新响应，不能无视贴身敌人一直偷晶。
5. 远程单位在有效射程内可站定攻击；停留必须对应攻击、蓄力或合法冷却状态，不能因敌人尚未走入射程就长期等在出生点。
6. 武器以浮游机、轮式炮车、机关车等外形表达移动能力。辅助型单位也有近敌普攻，治疗或护盾是附带周期技能。

水晶生命归零则该方失败。伤害按同一模拟步批量结算，两座水晶同一步归零记平局并可重试，不靠单位遍历顺序决定胜方。结果只结算一次，结算后停止生产和伤害。

建议超过 4 分钟后双方同步进入“晶核暴露”，提高对水晶伤害，推动结束；仍以真实水晶摧毁判胜，不用剩余血量替代。此机制需要验证长局与反推体验后再定参数。

建议首版每方最多同时存在 40 个战斗单位，达到上限时兵符显示“待出阵”，保留配方和完成进度，空出名额后按稳定次序补出。该限制是双方一致的战场容量，不是升级等级上限；最终值由目标手机测试决定。

## 4. 玩家与 AI 共用规则

AI 与玩家都维护灵石、残字、兵符、生产计时、水晶和军队；都通过同一个命令入口抽字、拼装、部署、合并、兑换。

- AI 不能直接创建单位、免费升级、跳过生产时间或恢复水晶。
- 常规关卡双方使用相同可用内容范围、基础属性与经济规则；可选配方相同，实际搭配可以不同。
- AI 只观察公开战场和自己的材料，不读取玩家手牌、未来随机结果或内部点击计划。
- 难度来自决策间隔、扩军与升级倾向、预留灵石、阵容搭配以及应对公开威胁的能力。
- 第一版使用可解释的规则优先级：先补齐可出兵配方 → 填补缺失角色职责 → 应对当前威胁 → 选择扩军或升级 → 消化积压残字。
- 简单 AI 较慢、组合单一；普通 AI 会完成配方和扩军；困难 AI 会根据近战压力、群体规模和敌晶状态调整投入。每次决策频率设上限，不用每帧无限操作获得手速优势。
- 教学暂停冻结双方；脚本教学只规定介绍顺序，不暗改敌方伤害。未来真人模式不支持单方暂停。

第一版不使用远程语言模型控制 AI，以保持离线可玩、低延迟和可复现。首领关也使用合法内容与命令，通过明确阵容风格制造挑战。

## 5. 美术与页面

### 5.1 视觉基线

国风 Q 版神话机关：角色用清晰剪影、大动作和标志法器；场景使用浮空仙岛、云海、青玉水晶和木铜工坊。友敌采用服饰边框、脚下阵营环和水晶造型共同区分，不能只靠红绿颜色。

所有现有画面重做，包括首页背景、章节地图、角色/机关、字块、图标、按钮、战场、图鉴和结算。保留题材不等于复用旧 Canvas 关节模型。

使用 Cocos 2D Sprite、预制体、分层动画和适量粒子；每种单位至少覆盖出生、移动、攻击、受击、技能与死亡。角色脚底阴影、受击闪色和弹道保证空间关系可读。最终画面不能用字符、简单几何占位或静态概念图冒充已完成角色。

横屏统一覆盖所有页面。游玩画面建议：顶部约 8% 为双晶生命和暂停；中部约 57% 为战场；底部约 35% 为工坊。比例通过手机效果图调整，主要操作热区约 44 CSS px 或等效尺寸。

工坊默认同时呈现灵石与抽取按钮、残字条、神将位与武器位。详细属性只在选中时显示；不常驻图鉴、战报、长规则或全目录。残字数量多时横向滑动，拖拽与滚动要有明确手势阈值。

### 5.2 页面职责

| 页面 | 主要内容 | 主操作与返回 |
| --- | --- | --- |
| 首页 | 动态仙岛、代表神将、当前章节进度 | 继续征战为主，选关、图鉴、玩法、设置为辅 |
| 选关 | 分章路径、锁定/已通关/当前关、奖励预告 | 点选关卡进入准备；回首页 |
| 准备 | 敌方战术、推荐职责、本局 3 将 2 器 | 开战；回选关，不叠加多层弹窗 |
| 战斗 | 双晶、自由战场、灵石、残字、生产位 | 场内拖拽与点选；暂停 |
| 图鉴列表 | 神将/武器分组、已解锁与剪影、配方提示 | 点条目查看详情；回来源页 |
| 图鉴详情 | 动态展示、残字配方、定位、技能、解锁关卡 | 演示或查看解锁位置；返回列表 |
| 玩法说明 | 抽字、拼装、升级、自动战斗四组短演示 | 按需翻阅、重播教学；回来源页 |
| 暂停/设置 | 继续、声音、震动、重试、回首页 | 离线明确继续；退出先保留可恢复快照 |
| 结算 | 胜负、新解锁、关卡勋章、一条有效提示 | 下一关/重试/选关/首页 |

首页不显示未实现的匹配按钮。全屏入口放在设置中，H5 使用公共全屏能力；原生小游戏不显示该按钮。暂停图标使用两根独立实心竖条，并保留“暂停”名称。

### 5.3 首次玩家引导

将引导嵌入第一关，控制在约一分钟的首轮学习目标；每次只高亮一个动作。

1. 点击“求将”，看到残字从灵石炉落入托盘。
2. 将「吒」拖入「哪□」，完成哪吒兵符。
3. 兵符入生产位，镜头短暂指向水晶，看到哪吒出生、前进和攻击。
4. 拼出离火铳，看到武器也从水晶出生并移动。
5. 用下一套残字把哪吒升至二级，突出等级与下一次出兵变化。
6. 指向敌晶：“击破它就获胜”，交还完整操作。

教程使用独立、公开的固定教学配给；正常对局使用真实随机规则。允许跳过和从玩法页重播。记录步骤完成，不因刷新重复发放可累积资源；恢复时校验状态，避免手势完成了但引导停住。

| 云台初阵 | 1–5 | 合字、出兵、升级、前排与远程组合 | 第 3 关巨灵神；第 5 关巡天机 |
| 山海交锋 | 6–10 | 扩军与集中升级，抗住持续推进 | 第 8 关杨戬；第 10 关震雷炮 |
| 天门破阵 | 11–15 | 分散兵群、范围攻击与破阵 | 第 13 关孙悟空；第 15 关寒霜轮 |
| 雷泽争锋 | 16–20 | 快速增援、减速与穿透配合 | 第 17 关雷震子；第 19 关雷鸣弩；第 20 关嫦娥 |
| 灵城攻守 | 21–25 | 前排保护、攻晶窗口与逆风补阵 | 第 22 关托塔天王；第 24 关护阵车；第 25 关破城锤 |
| 神机会战 | 26–30 | 护盾、续航、混合阵容与成熟 AI | 第 27 关九天玄女；第 29 关回春灯；第 30 关章节纪念 |

每章 5 关至少包含“观察新组合 → 针对性练习 → 内容解锁 → 新旧组合应用 → 综合对手”。第一章逐关为：合字攻晶、升级选择、前排压力、前后排协作、完整小对局。

关卡差异由敌方编队、AI 决策风格、允许的本局内容和挑战目标构成，不只是不断增加敌方生命。早期为双方限制同一内容池；后期玩家可从已解锁且本关允许的内容中组队，AI 也有对应合法选择。

通关只要求摧毁敌晶；额外两枚勋章采用该关独立的可选目标，例如保住指定比例晶血、用神将与机关共同击杀、在目标时间内结束。勋章不阻塞下一关，重试不重复发首次解锁奖励。时间目标不是主胜负条件。

每关配置包含稳定 ID、章节、前置关卡、可用目录、初始资源、AI 编队与策略、场景引用、通关奖励和勋章条件。校验解锁图无环、奖励无重复、配方完整、AI 内容合法，并证明每个关卡都存在无需未来奖励的胜利策略。

### 6.3 图鉴承担实际决策功能

- 神将和武器共用对应内容目录，不维护另一套名称、配方和属性。
- 未解锁：剪影、角色职责、明确解锁关卡；已解锁：完整形象、残字配方、技能说明与动作预览。
- 详情给出“适合处理什么威胁”和“一组可用搭配”，不堆十几行属性；数值详情按需展开。
- 记录使用次数、最高局内等级和已完成挑战；这些是收藏与熟练度记录，不增加对战攻击力。
- 新解锁在结算中集中展示一次，点击可到图鉴或加入下局编队，不连续弹出奖励窗。
- 在准备页查看图鉴后回到原编队，不丢选择；离线战斗中仅通过暂停进入说明与图鉴。

## 7. Cocos 与未来对战的技术组织

### 7.1 工程边界

采用仓库已有的 Cocos Creator 3.8.8 + TypeScript 基线；从一个 Cocos 工程产出 Web Mobile 与目标小游戏平台版本。版本依据当前仓库工程和发布约束，不声称它是官方最新版本。

建议目录如下，实施时优先沿用现有项目工具，不增加独立通用框架：

```text
games/local/merge-front/
  assets/scenes/             Cocos 启动场景
  assets/prefabs/            页面、兵符、神将、武器、特效
  assets/art/               UI、角色、章节场景与图标
  assets/audio/
  assets/scripts/
    core/                   纯 TypeScript：状态、命令、经济、合成、生产、战斗、胜负
    content/                神将、武器、残字、关卡、AI 配置与 schema
    ai/                     观察与合法命令决策
    view/                   Cocos 页面、渲染、触屏、音效、演示
    platform/               Game Host、本地存档、生命周期与平台接入
  scripts/                  构建、素材校验、生产预览
  tests/                    规则、内容、回放、浏览器
  docs/design/              方案、效果图、逐页对照与验收记录
```

`core/content/ai` 禁止导入 `cc`、DOM 或渠道 SDK。核心可以直接在 Node 测试与未来服务端运行；Cocos 负责输入表现和渲染。先用少量职责清楚的模块，避免给每个状态创造管理器。

页面布局使用 Widget、Layout 与 SafeArea；章场景和角色资源按 Asset Bundle 拆分，首屏只加载首页、公共 UI 和第一章必要资产。此使用方向与 Cocos 官方 [SafeArea 文档](https://docs.cocos.com/creator/3.8/manual/en/ui-system/components/editor/safearea.html) 和 [Asset Bundle 文档](https://docs.cocos.com/creator/3.8/manual/en/asset/bundle.html) 一致。微信等平台的胶囊区域仍需适配层补充，不能认为 SafeArea 自动解决所有宿主遮挡。

角色和特效复用节点；首版按有限单位数量实现简单邻近查询，只有实测显示查询成为瓶颈时才增加空间索引。逻辑 20 Hz 为初始预算，渲染插值独立，最终性能目标用目标设备测量。

### 7.2 从人机就开始固定命令边界

```text
触屏操作 ─┐
          ├→ 命令校验 → 同一个 MatchCore → 状态/事件 → Cocos 画面
AI 决策 ──┘

未来：网络玩家命令 → 服务端 MatchCore → 公开快照＋本人私有状态 → 两端画面
```

命令包含对局 ID、己方身份、序号、规则版本和动作参数；动作限定为抽取、填字/撤回未完成材料、部署、合并和兑换。调用方不能提交结果等级、伤害、灵石余额、出生单位或胜负。

固定模拟步、稳定实体 ID、稳定同距排序、可序列化随机源和顺序一致的伤害结算从第一版落实。坐标和逻辑时间采用明确量化精度，不依赖动画回调决定命中。双方抽取使用独立随机流，避免一方多操作改变另一方的随机序列；离线回放记录种子、配置版本与带执行步号的命令。执行步由模拟端分配，未来联网由服务器分配，不能接受客户端随意回填过去的操作。

首版必须验证：相同配置、种子和命令重放得到相同结果；在 Node 与 Cocos 构建端核对关键状态。固定步本身不自动证明跨运行时确定性。

未来对战推荐服务端权威模拟：服务器校验命令、抽取残字、计算战斗和结算；客户端插值展示。服务端只发送公开战场和该玩家自己的私有材料，不暴露对手手牌和未来随机种子。协议处理重复、乱序、过期命令及重连全量快照。

局内等级每局重置；后续公平房间采用共享合法内容池或房间内临时开放内容，不能让老玩家永久数值优势进入同一标准赛制。离线存档不能直接成为联网战绩或可信解锁凭证。

第一版实现本地命令处理、快照和回放验证即可；不提前搭建匹配服务、微服务集群、排行榜和赛季。将来从好友房开始，再增加匹配与规模测试；有命令边界不等于已经具备大量玩家承载能力。

## 8. 平台、存档和现有调用方

- 复用 Game Host 的存档、导航等契约；独立运行提供本地适配，Shell/iframe 走现有宿主边界。存储不可用时可继续当前本地对局。
- H5 横屏支持普通横屏与竖屏视口的旋转容器兜底，映射拖拽坐标；全屏请求失败仍可玩。原生小游戏使用宿主方向配置与安全区，不调用浏览器全屏。
- 暂停、切后台和退出清空触点与音频，离线冻结模拟并按需保存；恢复不补算后台经过时间。未来真人对局由服务端持续运行，重连恢复状态，两种语义分别处理。
- 新存档版本分开保存设置、进度和人机对局快照。迁移旧音效偏好，将旧胜场保留为历史统计；旧胜场不能映射成不存在的章节三星，不删除原始记录。
- 快照固定内容版本和随机状态，校验后恢复；无法迁移的旧对局允许重新开局，保留已确认的关卡与解锁数据。结算与首次奖励按对局 ID 幂等。
- 支持统一 `SmallGamesDev` 的 URL/存储开关；调试跳关和任意等级只在显式开发模式开放，调试结果与正式成长隔离，不手改公共同步副本。

用户已授权实施并推送dev，本轮按“方案 → 效果图 → 代码 → 实际截图与功能校验 → 发布”推进。C 阶段是验证核心体验的里程碑，不能用它代替 D 阶段的完整内容交付。

### 核心验收清单

1. **合成经济**：配方两字/三字/四字、配方内同字不同字位、重复材料、跨配方拒绝、1＋1/3＋5/高等级、撤回和触摸取消、扣费幂等、保底与兑换双方一致。
2. **战场行为**：斜向接敌、近敌切换、远程接近、出生疏散、近战包围、无目标推进、武器移动、攻晶受阻转火、双晶同帧归零、结算后无伤害。
3. **生产升级**：阵亡不丢兵符、升级只影响新兵、合并/移动不刷生产、人口满等待且不吞进度。
4. **AI 公平**：通过与玩家相同命令，资金守恒、合法内容、行动频率、无法读取私有玩家材料；换边与多随机种子检查规则偏置。
5. **内容平衡**：所有关卡可达、奖励不重复、每种单位有使用场景；至少比较扩军流、集中升级流、前排远程流与混合流。先串行运行批量模拟，再用真实玩家体验修正，模拟胜率不能替代手感判断。
6. **手机操作**：至少 844×390、740×360、568×320 横屏，以及 390×844、320×568 的旋转兜底；全页面往返、拖拽、滚动冲突、多触点取消、后台恢复和进度恢复。
7. **视觉验收**：逐页与效果图并排对照，保存实际截图；检查兵符区不遮挡战场、字块可读、近战/远程可区分、暂停图标正确、图鉴展示是真实可加载素材。
8. **生产运行**：运行本游戏规则/内容/回放测试、真实 Creator 构建和触屏浏览器流程；新入口执行 `check:dev-mode`、`test:dev-mode`、`test:dev-mode:browser`；修改公共全屏时执行 `test:h5-fullscreen`。
9. **发布**：同步远端 dev，记录准确 base/head，执行相关 `validate:candidate`，正常推送，不 force push；远端前进则重新合并复测，CI/Pages 与真机验收分开报告。

## 10. 风险与明确不做的内容

最需要实测的是三个交叉点：无限累加与有限生产位是否让单一高等级无脑获胜；随机残字与实时操作是否让玩家来不及决策；二维自由移动是否发生卡位、拥挤和前后排完全失效。

通过可控本局残字池、公开保底、线性成长、稳定寻敌与首章验证降低这些风险，不能仅凭方案宣称已经平衡。美术工作量也必须以可复用动作、图集和页面规格约束，避免只有首页精美而战场仍是占位图。

第一版不做真人匹配、排位赛季、付费抽卡、公会、永久战力养成、复杂装备合体和全 3D 场景。保留实现玩家对战所必需的规则隔离与命令边界；具体平台真机、负载容量和网络对战均需后续单独验收。
