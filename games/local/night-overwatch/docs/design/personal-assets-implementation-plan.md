# 夜航守望 · 分批实施计划

更新：2026-11-01。当前状态：**六批运行代码已实施，本地后端与 FRP 已验证**。本轮按用户指定的 `358b1fe0` 执行；实际证据见[实现验收](../verification-2026-11-01-progression.md)。生产、真机、真实广告及 TapTap 打包不在本轮已验收范围。

**目标：** 在保留原积分、旧进度与身份边界的基础上，完成个人成长、军需商店、金币/视频礼包套餐、任务、个人技能及补偿信箱的完整闭环。

**架构：** 复用现有Cocos纯规则、单人服务端回放、双人权威模拟、身份与公共广告端口。资产独立记账，商品/效果/库存/配装分离；每场使用服务器确认的配置快照，不建立额外通用平台或新货币。

**技术栈：** 现有TypeScript、Cocos Creator 3.8.8、Runtime API与PostgreSQL；实际Node/pnpm及发布候选规则按[项目增量发布规范](../../../../../docs/operations/incremental-publication.md)执行。

产品依据：[当前方案](2026-10-29-personal-assets-plan.md)。页面方向：[九张关键概念图](progression-2026-10-31/README.md)。本计划中的新增文件名是建议落点，实施前先检查同职责现有模块，避免重复创建。

## 批次1：资产、经验与权威结算

### 具体步骤

1. 只读核对线上真实部署、数据库表/旧钱包记录和历史结算来源，确定补偿截止点；不以Git回退推定数据已回退。
2. 固定金币、经验、等级、有效完成/失败/平局/退出及不同模式收益规则版本，保留原积分公式。
3. 扩展独立钱包、奖励流水与等级资格；按现有迁移方式增加数据结构。添加同玩家同来源奖励唯一约束。
4. 在单人回放认可的结束事件和双人/服务器人机结算事务中计算收益，不能仅覆盖单人成功通关。
5. 增加个人资产查询和结算回执，客户端显示积分/金币/经验独立列及已到账/待同步状态。
6. 补充失败、重复提交、丢响应、双设备、切账号晚响应的最小验证，再检查旧积分记录不受影响。

### 文件与消费者

- 服务端：`services/runtime-api/src/competition/ranked-store.ts`、`ranked-runs.ts`、`night-ledger.ts`、`ranked-types.ts`、`types.ts`、`game-routes.ts`。
- 拟新增：同目录夜航资产/奖励模块，优先复用回退前钱包事务和幂等思路，不整体恢复旧产品规则。
- 游戏：`games/local/night-overwatch/assets/scripts/Online.ts`、`Overwatch.ts`、`HUD.ts`。
- 共享客户端：`platforms/competition/game-services.js`及对应接口测试。
- 回归起点：`services/runtime-api/tests/night-online.integration.test.ts`、`ranked-control.test.ts`及游戏`tests/online.test.ts`。

**退出条件：** 相同对局重试只能入账一次；没有金币/经验覆盖积分的路径；客户端不能自报可信余额；失败奖励与退出规则均实际覆盖。生产迁移未执行不标记线上完成。

## 批次2：商店、库存、礼包套餐与签到

### 具体步骤

1. 定义商品/效果/资格/来源白名单，列清单场、24小时、永久标签及同效果去重。金币限定两连发/双弹道不进入免费或视频来源。
2. 实现金币购买和发货事务、数量库存、限时激活/续期、永久已拥有状态及回收；重复请求返回原订单结果。
3. 实现普通/精良/稀有/史诗礼包的版本化概率与内容池，金币直接入账，其他均为单场物资。
4. 增加1、3、5、10、20个套餐，按同一报价版本显示总价、单价、折扣；测试最大折扣下的回收和任务链无套利。
5. 将H5服务端观看凭据核查作为接入前置：可验证时严格验凭据及唯一性；不可验证时先明确限额、订单绑定、回调去重、异常监测等受限方案，记录无法证明真实观看的剩余风险，不能把随机challenge或完成回调称为可信观看证明。再接公共视频端口，多段视频绑定订单，完成全部条件后只发一次；关闭、刷新、跨日后保留已确认进度。
6. 接每日累计签到；以服务器北京时间日键去重。
7. 制作商店、套餐、签到、仓库、出售、概率详情及多段视频进度/失败状态；训练试用入口与第4批对接。

### 文件与消费者

- 拟新增：Runtime竞争服务目录内商品/库存/礼包及视频兑换订单模块，不建立通用商城微服务。
- 现有：`game-routes.ts`、批次1资产模块、`platforms/competition/game-services.js`。
- 游戏：`Platform.ts`、`Online.ts`、`HUD.ts`与需要的专用页面模块。
- 广告：复用`platforms/h5/platform-ads.js`及现有奖励Host；仅实际修改公共行为才扩大对应消费者回归。

**关键检查：** 扣币与发货原子一致；商品已永久拥有不会重复收费；礼包重试不会重抽；视频重复/迟到回调不会重复计数；订单切换不能复用观看；未完成不发整套；金币方式与视频方式各自实际可用；广告无库存不阻断普通玩法。

**退出条件：** 获取→购买/兑换→开包→库存→出售闭环成立；多段视频失败恢复和最优惠套餐回收检查通过。凭据可验证/不可验证采用哪条路径须有证据和明确风险记录；限额与回调防重不能宣称防伪观看已解决。模拟SDK通过不等于真实宿主观看与库存验收。

## 批次3：两套军需与每场消耗契约

### 具体步骤

1. 实现单人/双人独立保存，初版按整套方案2个改装、1个特种武器、1个技能，基础成长不占槽。
2. 校验相同效果不能借来源/期限/名称重复装备；显示最终发数、耗弹与热量预览。
3. 服务端开局预留库存，正式开始扣耗并生成不可变配置快照；未开局取消释放，服务器无效局按规则返还。
4. 接入单人回放与双人房间启动；同对局重连不再扣，客户端不可自行扩大配置。
5. 库存不足/过期时保留可玩基础方案并说明，不自动买货；局中编辑只影响下一场。
6. 制作独立军需页、自动消耗说明、替换/互斥/库存不足状态；模式页只展示方案摘要，不串行强制配装。

### 文件与消费者

- 游戏：`Overwatch.ts`、`Online.ts`、`HUD.ts`，及纯规则配装校验模块（按实际已有职责落点）。
- 核心：`assets/scripts/core/Replay.ts`、`Duel.ts`。
- Runtime：`ranked-runs.ts`、`ranked-types.ts`、`store.ts`、资产/库存模块与`game-routes.ts`。
- 回归：游戏现有`tests/replay.test.ts`、`duel.test.ts`、Runtime夜航集成测试。

**退出条件：** 保存不扣耗、自动应用不自动购买；并发双设备不超卖；预留物品不能出售；同场重复连接不返还/重扣；永久资格不浪费对应单场库存；24小时开局快照和下一局失效正确。

## 批次4：成长效果、个人技能与新增武器

### 具体步骤

1. 将现有全局buff状态拆为每位玩家持有的效果、持续时间和冷却；保留原暂停/权威模拟语义。
2. 实现统一效果合并与适用武器白名单；两连发与双弹道允许组合，按实际发数耗弹/发热，范围与保护区检查使用最终有效半径。
3. 复用现有追踪行为实现永久/单场资格的新技能入口；仅冷却，无次数限制；保留旧单人广告追踪独立来源且不重置技能冷却。
4. 实现电磁干扰技能，仅短时地面定身及明确抗控；不改真实通信、不顺带禁攻击、不影响已发弹丸。
5. 实现无人机有限寿命/伤害预算及减速，激光合法目标即时伤害及弹药/冷却。
6. 将新增指令、版本和快照同时接入客户端、服务端、回放、重连、机器人；同时实现最快纪录的规则版本落库、旧纪录历史保留、榜单按版本查询及客户端展示。成长版不能直接与旧版本混排，原积分排序不变；不只接入画面。
7. 制作战斗HUD技能可用/生效/冷却状态和武器表现效果图，再实现并对照；接训练试用，不消耗或产出正式资产。

### 文件与消费者

- 核心：`Data.ts`、`Simulation.ts`、`Duel.ts`、`Replay.ts`。
- 输入与呈现：`Actions.ts`、`Overwatch.ts`、`HUD.ts`、`World.ts`、`Effects.ts`、`Presentation.ts`（以实际调用关系为准）。
- 服务端：`services/runtime-api/rules/night.mjs`、`night-ranked.mjs`及启动快照/指令验证；最快榜涉及`ranked-store.ts`、榜单查询路由和游戏`Online.ts`/`HUD.ts`展示。
- 现有测试起点：`combat-buffs.test.ts`、`homing.test.ts`、`duel.test.ts`、`replay.test.ts`、`fire-zones.test.ts`。

**退出条件：** 双方效果隔离，个人养成真实生效；重连/切武器不重置冷却；单人暂停冻结而双人继续；同效果不重复；弹药不足不能凭连击免费发射；地形、友伤、保护区和目标死亡均正确；既有广告补给仍可用且未扩展到双人。

## 批次5：任务、成就、公告和补偿信箱

### 具体步骤

1. 根据结算、签到、开包、观看等唯一事件建立任务模板与进度；复用事务或可重试记录，不新建通用消息总线。
2. 服务器每账号每日生成并保存3～5个可完成目标，支持好友/视频替代任务；定义跨日归属与历史领奖窗口。
3. 实现直接领奖、一键领取及有限长期成就；无活跃指标，永久奖励每档一次。
4. 实现公共公告和个人邮件，区分未读/已读与附件待领/已领。
5. 使用批次1核对的历史来源计算补偿，先只读预演输出每玩家金额/附件与重复检测，再执行迁移版本唯一的发信。
6. 接入补偿领取事务与红点；不清除原积分、存档、已获得广告资格和可验证旧资产。

### 文件与消费者

- 拟新增：Runtime夜航任务、成就、消息及补偿模块，继续复用现有身份/资产服务。
- 事件来源：`night-ledger.ts`、`ranked-store.ts`、签到/礼包/视频订单模块。
- 客户端：`game-services.js`、游戏`Online.ts`及对应页面。
- 回归：Runtime夜航集成测试与任务/邮件专用最小用例；游戏任务/消息的真实入口交互检查。

**退出条件：** 刷新/重启不重抽任务；同一事件不会重复推进；没有不可能的强制组合；阅读不等于领取；多设备只能领一次；补偿按玩家和迁移版本唯一；账号绑定不会重复领或合并另一账号资产。

## 批次6：首页整合、兼容与发布候选

### 具体步骤

1. 按当前已评审图完成首页：上军需准备、下开始行动，右侧每日签到和礼包；模式选择与准备互不串联。

3. 以旧账号、新账号、永久技能已拥有者、库存不足者、离线/重连者跑通完整循环。

5. 验证单人最快榜规则版本边界、原积分排序、玩家公开字段白名单；避免余额、库存和凭据泄漏。
6. 依据最终实际变更选择最小相关规则/类型/构建/浏览器检查；不无关重复全仓。
