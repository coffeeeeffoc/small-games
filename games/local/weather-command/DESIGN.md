## 1. 想让玩家真的做什么

在一个装着补给船的气象沙盘上，最多下达三次天气指令，把船停进亮着灯的码头。玩家拨动水位、改变滑行条件，并直接从船身拖出风向；亲眼看见船浮起、撞碎木栅、滑过岔口或准确停靠。

目标体验是“我改变了环境，所以这条路线现在能走”，而不是认出三张正确的牌。没有倒计时压力。教学关约 20–45 秒；后续单关目标 1–3 分钟，包含观察、执行和一次重试。时间是待测目标，不能作为已达成指标。

“最多三次”指三次有效天气操作，不要求凑满三次；连续两次不同方向的阵风分别计一次。UI 使用“天气指令 3/3”，避免“只能切换三种天气”的歧义。

## 3. 最小规则：四种天气都必须有用途

### 3.1 场景与状态

- 沙盘是至多 7×7 的平面航道网格，格线只在预演时轻显。墙、码头、低桥、脆木栅在地图上直接可见。
- 全图只有一个连通水体，共用水位 `H = 0 / 1 / 2`，分别表现为干涸、浅水、高水。没有不同区域的水凭空不相通。
- 全局另有“普通 / 冰雪”状态。下雪后，干涸航道铺雪，有水航道结冰；船可在冰雪上滑行。这是桌面玩具式规则，不模拟真实结冰时间。
- 一艘补给船：位置、停靠状态。船底做成宽平滑底，明确表现出能浮、也能在雪面滑；不借助看不见的轮子移动。
- 木栅是可移除地形，其余地形固定。没有每关独有的对象反应表。

### 3.2 天气与规则表

| 指令 | 状态变化 | 船的结果 | 可读反馈 |
| --- | --- | --- | --- |
| 雨 | 水位 +1，上限 2；同时清除冰雪 | H 从 0 到 1 时船浮起；雨本身不横向推船 | 水面上升到刻度，船升起，浮起的一声轻响；预演同时标出“涨水、融雪” |
| 风 | 水位和表面不变；玩家选择上、右、下、左之一 | 普通水面最多推进 3 格；冰雪面沿直线滑到障碍；不能自动转弯 | 拖出箭头、落点虚影、船摆动与尾迹；冰上滑行声变长 |
| 太阳 | 水位 -1，下限 0；同时清除冰雪 | 降水位可通过低桥；H=0 时船会搁浅 | 阴影缩短，水线降低，桥洞出现可通行标记；预演明确显示可能搁浅 |
| 雪 | 水位不变；全场进入冰雪状态 | 从水上短推变成长滑；H=0 的雪面也能滑船 | 水面由波纹变冰纹，裸底铺雪，船身轻轻落稳；预演改为长滑轨迹 |

雨和太阳兼有融雪，是本方案最需要试玩验证的规则负担。它们都被定义成“偏暖天气”；按钮和预演必须写出两个效果。如果玩家持续误解，第二轮应简化模型，而不是补长说明。第一轮暂保留它，因为第 5 关需要用雨把长滑改回短推。

### 3.3 地形规则及动作结算

- **墙**：停在墙前一格；撞墙不损伤，回弹一下。水位不能淹过墙。
- **低桥**：H≤1 可通过，H=2 时挡住船；冰雪不会降低船所处高度。桥柱带两道水线，高水时碰撞处高亮。
- **脆木栅**：移动中的船接触后撞碎并进入该格，不额外扣移动格数；破碎后永久消失。雨、太阳、雪不能隔空毁掉它。
- **码头**：必须在一条指令完整结算后停在接收格才算送达。冰面从码头前滑过不算停靠；码头清楚标“停在这里”。
- 普通状态 H=0 的船不能被风推动；冰雪状态 H=0 可以。普通有水时每次风最多走 3 格，遇墙或高水低桥提前停；冰雪时一直滑到障碍前。
- 只有全局表面，不存在一次滑行跨越干地、水面、冰面时偷偷切换算法的情况。
- 指令先计算完整结果，再依次播放水位、浮起、运动、撞栅、停靠等事件。播放中不能追加指令，避免帧率或连点改变结果。
- 确实完全无效的操作不扣次数：例如干地吹风、已是冰雪再下雪、H=2 普通状态再下雨。显示原因。H=2 但仍有冰雪时，下雨能融雪，属于有效操作。
- 风被紧邻障碍完全挡住且没有破坏木栅，也不扣次数。有效但走错方向、滑过岔口、升水封桥的指令会扣次数。
- 有效指令结算后先判停靠，再判次数耗尽；第三次到达必须算赢。

这不是隐藏惯性参数的物理模拟。距离、桥洞和冰雪摩擦都要稳定到可以用肉眼预测。

## 4. 30 秒实操与触控方式

以第 2 关为例，初始干涸，船在左下方，码头在右上方，两条路都看得见。

| 时间 | 玩家操作 | 即时反馈与思考 |
| --- | --- | --- |
| 0–4 秒 | 看见码头脉冲、船底搁浅，以及“三次指令” | 目标只有“把船停进码头”；不用先读任务弹窗 |
| 4–9 秒 | 点击“雨” | 单步预演标出涨水和浮起；再次点击同一按钮确认，水涨、船浮，剩 2 次 |
| 9–16 秒 | 按住船，向右拖动后松手 | 箭头吸附到右方，虚影落在 3 格外的岔口；船推进并轻晃停稳 |
| 16–23 秒 | 从船向上拖动后松手 | 船沿下路撞碎木栅，碎木溅开，随后进入码头 |
| 23–30 秒 | 看停靠灯亮、听到短铃；点击“再试另一条路” | 用“雨→上风→右风”走上路；也可尝试雪后为什么不能先向右 |

- 雨、太阳、雪采用“点击选中并预演 → 再次点击同按钮施放”。没有额外确认弹窗。切换按钮免费，点击沙盘空处取消。
- 从船身或船周围扩大的触控圈直接拖动即可使用风，不必先选“风”。底栏保留风按钮供可发现性与替代输入使用。
- 风拖动量只决定方向，不控制力度；小于阈值就取消，避免玩家误以为拖得远吹得强。
- 风按钮选中后，在船旁显示四个不小于 44 CSS px 的方向按钮；触控、鼠标和键盘都可操作，不要求精细拖拽。
- 移出画面或 `pointercancel` 取消预演并释放捕获，不扣次数；一次手势最多提交一次。第二根手指不能重复施放。
- 当前指令的预演显示路线、落点、阻挡及预计破坏，不显示完整三步答案。预演与正式执行必须调用同一个规则函数。
- 预演很准确会降低谜题难度；这里接受它来换取可预测性，必须靠跨两三步的路线选择成立，不能靠隐瞒结果制造难度。

## 5. 能重复玩的决策，以及诚实的边界

1. **选哪条航道**：同一组天气指令，两个风向顺序可走不同的格子、撞不同的障碍。路线必须在沙盘上可见。
2. **停在岔口还是滑到尽头**：水面精确推进 3 格；雪面能到远处，但可能滑过转弯口。雪不是纯升级。
3. **花一次改变环境，还是把三次留给行船**：第 3 关可以退水穿桥，也可以不改水位绕桥。
4. **保留当前冰雪，还是融掉它**：第 5 关可以利用已有雪面走上路，也可以下雨改成短推，走下路。

没有卡牌抽取、随机天气时钟或随机生成“必有解”的承诺。先做下面 5 张小图。固定图解出之后的价值主要是试另一条路线，不能宣称无限重玩；长期留存尚无依据。

如果试玩者每关都不看地形，只试几组天气名字就通关，核心设计判失败。第二轮优先调整航道与落点，不用加星级、签到或文案掩盖问题。

## 7. 失败、撤销与声音反馈

失败只发生在三次有效指令用尽且船未停靠时；本原型不额外加生命、船体耐久或付费复活。有效但无解的中间状态不提前给出全知式提示。

失败后保留沙盘，船和目标同时标记。根据实际事件写短原因，例如“指令用尽：刚才在雪面滑过了转弯口”，或“指令用尽：船还没有停进码头”。没有发生的碰撞或滑过事件不能凭空写入解释。

按钮只有“撤销上一步”和“重新开始”。撤销恢复完整状态：位置、水位、冰雪、木栅、剩余次数；重试不播放长进场动画。没有失败广告。

动画目标：选择后立即出现反馈；水位变化约 0.6–0.9 秒，航行约 0.8–1.4 秒，撞栅有短暂停顿、碎片和水花。短暂停顿是演出，不改变模拟结果。降动态效果时取消镜头晃动，保留位置与状态过渡。

声音用 Web Audio 生成短音与噪声，不依赖远程资源：雨点、阵风、冰滑、木栅断裂、靠岸铃各有区别；一次用户手势后解锁。静音按钮常驻且保存选择。音频不可用时照常游玩；声音不能成为唯一规则提示。

## 8. 美术：桌上的珐琅气象沙盘

**主方向：暖色气象站桌面上的实体玩具。** 奶油色珐琅边框、深靛蓝轮廓、青绿色浅水、橘红补给船、蜂蜜色低桥和木栅；雨雪不是全屏蓝色滤镜，而是真正改变沙盘表面、船身高度与运动残影。

地图保持正交俯视，边框、墙体只有小幅厚度阴影，避免等距透视遮住岔口。船有白色补给箱和橙色小旗；码头用灯塔灯圈与靠泊缺口辨认。雪是略带蓝灰阴影的颗粒白，不能覆盖桥洞、木栅和目标。雨滴限定在航道内，避免淹没触控反馈。

手机竖屏布局：上方一行“天气指挥部 / 指令 3/3”；中部沙盘占主要面积；下方一行短提示与四枚大天气按钮；最下方撤销、重来、静音。游戏进行中没有大厅、长目标卡、任务列表或数据仪表盘。

**备选方向：剪纸海岛气象剧场。** 用纸张层叠与简单折纸船呈现水、雪和桥洞，素材成本更低；风险是波纹、雪层和纸船的高度差不易辨认。只有主方向在 SVG 中代价过高时才选它，不混搭两套视觉。

## 9. 后续最小独立技术实现（尚未开始）

建议零依赖原生 HTML/CSS/ES modules + SVG 沙盘。7×7 的地形与单船不需要 Canvas 引擎；SVG 便于触控命中、路径虚影和动画，HTML 承担按钮、标签与无障碍名称。

预计文件：`index.html`、`style.css`、`game.mjs`、`rules.mjs`、`levels.mjs`、`server.mjs`、`check.mjs`。不创建通用 ECS、场景框架、组件库或插件接口。

- `rules.mjs`：输入状态与一条指令，输出新状态、有效性与事件。函数不读 DOM、时钟、音频或随机数。
- `game.mjs`：触控、预演、实际提交、SVG 动画、声音与简单撤销。预演执行同一规则但不写当前状态；提交后按规则事件演出。
- `levels.mjs`：关卡起始状态和地形。不能放“第几关时风特殊处理”或预写通关动画。
- `server.mjs`：只用 Node 标准库从本目录提供静态文件，默认端口 4402；校验请求路径不越出本目录，正确返回 ES module MIME；端口占用时明确报错，不偷偷改端口或结束别的项目进程。
- `check.mjs`：Node 内置 assert 的一个可运行检查入口，验证纯规则与关卡；不引入测试框架。

输入边界要校验天气类型、四向方向、次数和地图数据；非法指令不能破坏状态。切换关卡或撤销后，旧动画回调不得再次写回旧状态。切后台时暂停演出，回前台对齐已提交的逻辑状态；不按经过的真实时间多走一段。

存储仅限本机静音设置与已过关标记，存储失败不阻断游戏；不做账号、后台、排行榜、广告、支付和平台 SDK。不依赖兄弟目录的包、服务器、资源或构建产物。

### A. 一条 Node 自检命令覆盖核心逻辑

`check.mjs` 至少完成：

1. 按本文五关的候选解执行，验证正确的最终位置、木栅状态、消耗次数和胜负。
2. 同一初态与指令重复计算结果一致；预演不改变传入状态，正式执行与预演的完整结果一致。
3. 第 2 关雪后右风停在 `(5,5)`，雨后右风停在 `(4,5)`；随后上风只有后者能走下路通关。
4. 第 3 关 H=2 的直接右风被桥阻挡；退水后可过；绕行的三个风指令也可完成。
5. 第 4 关雨、右风、右风确实耗尽失败；雪、右风、上风确实成功。第三次到达必须判胜，不能先判耗尽。
6. 无效指令不扣次；有意义的融雪仍扣次；撤销能恢复被撞碎的木栅及所有天气状态。
7. 穷举每关最多三条指令，单步有雨、太阳、雪及四个风向，共 7 个候选，深度 3 最多 343 个完整指令序列。无效动作剪枝，不把它算成额外解法；打印解的数量及真实经过的路线。第 2、3、5 关必须各出现至少两条不同空间路线。

穷举能证明规则下有解与多路线，不能证明游戏好玩。

## 12. 第二轮挑战回应与第三轮收敛（最终执行版）

1. **双效果与雪万能问题**：按钮直写“雨 / 涨水·融雪”“太阳 / 退水·融雪”，动画同时呈现表面解冻与水线升降。保留全局规则，不指定必须使用哪种天气。第 2 关雪会滑过下路岔口；第 3 关雪后两阵风不足以绕高水低桥，太阳退水则能走捷径，穷举验证这些反例。
2. **连续连锁**：雨水上涨时船身连续浮起；风以连续位移推进，接触木栅才破碎，之后继续航行并停靠。状态离散，动作不能格子瞬移；所有演出来自真实规则事件。
